## Context

当前“频道”就是 `workspaces`（name/repo/description + 角色成员 read/write/admin），没有消息；任务会话是唯一的多 Agent 协作面。运行期核对表明 workspace 基本空转：前端建任务不绑定它，worktree 用 `task.repo`，workflow dispatch 绕过成员守卫，access 只影响 claim/自动派发。

现有知识体系：

- 作用域只有 `role`（notes/MEMORY，严格按 role_slug 隔离）、`task`（task snapshot，仍按角色隔离）、`repo`（lessons）、`shared`；**没有频道级知识**。
- 没有 `authority`（约束/参考）语义；repo 目录由 workspaces/lessons/notes/tasks/文件系统派生；任务可绑最多 3 个 knowledge repo（`task_knowledge_repos`）。
- 任务内多角色不能共享同一份 task 知识；新建角色不继承知识；角色删除保留知识；角色禁用不影响知识检索。
- 跨角色知识通道只有人工批准的 lessons。

用户已确认的方向：

- **不删频道、不改名为项目**；保留 `workspaces` 表/API/页面与 `workspace_id`，在现有结构上扩展。
- **频道 = 任务归属 + 频道知识收割 + 频道资产管理**：建任务时把任务归到频道；频道页面管理频道级资产；任务完成后可把知识收割到频道。
- **频道知识 repo 可被其他任务/频道引用**；绑定频道的任务把频道约定视为 normative（必须遵守），只引用 repo 的任务视为 reference（仅供参考），必须显式标记。
- **任务知识**在任务参与角色间共享；**角色知识**私有。
- **个人知识必须通过 action + 成功实践 + 提炼写入**；不允许直接复制其他角色 notes、频道知识或 skill。Skill 是能力固化，不是个人知识。
- **不做角色禁用/知识引用开关、不做 role archetype/模板继承、不做直接导入**。

论文依据：频道 workflow/SOP 复用有 AWM (arXiv:2409.07429)、Experiential Co-Learning (arXiv:2312.17025)、IER (arXiv:2405.04219)、G-Memory (arXiv:2506.07398)、MAEL (arXiv:2505.23187) 支撑；任务内共享有 AutoGen (arXiv:2308.08155)/MetaGPT (arXiv:2308.00352)/MAST (arXiv:2503.13657) 支撑；角色私有经验有 ExpeL (arXiv:2308.10144)/Voyager (arXiv:2305.16291)。风险来自 Lost in the Middle (arXiv:2307.03172)、Memory survey (arXiv:2603.07670)、AgentPrune (arXiv:2410.02506)：上下文噪声、总结漂移、冗余成本。

## 核心模型：Scope × Kind × Authority × Practice Gate

| 作用域 | 内容 | 读取 | 写入 |
|---|---|---|---|
| **Global/shared** | 人工批准的 lessons | 所有角色 | propose + human approve（现有） |
| **Channel/domain** | 约定、workflow/SOP、角色需求、关键决策、陷阱 | 绑定该频道的任务 + 引用该频道 knowledge repo 的任务 | human/agent propose，human 批准；可从任务收割 |
| **Task/instance** | 任务规则、算法、决策、交接、产物 | 该任务参与角色 | 任务参与角色；任务结束归档 |
| **Role/agent** | instruction、MEMORY、notes、技能、经验 | 仅本人；human 可审计；后续可作为只读参考 | **实践门控**：action + 成功实践 + 提炼 |

Authority：

- `convention` 默认 `normative`：**只有绑定该频道的任务**把它渲染成“约束（必须遵守）”；只引用该频道 knowledge repo 的任务渲染成“参考”。
- `workflow/sop`、`role_requirement`、`decision`、`insight` 默认 `reference`；workflow 由 Cindy 选用，role_requirement 只是建议知识，**不做硬角色池**。
- 所有条目在提示词/UI 中显式标注“约束”或“参考”。

Practice gate：

- 角色可以**只读理解**频道/任务/其他角色的知识，但不得直接写入自己的知识库。
- 个人知识写入必须带 `practice_task_id` / `practice_run_id` / `outcome` / `verified_at` / `source_knowledge_ids`（存为 `source_knowledge_json`）；任务/run 未成功时只能写成 draft，不进入 CIC。
- Skill 继续存 `role_tools`，不是个人知识；应用 skill 后的成功实践结果可提炼为个人知识。
- 无“导入某角色 notes”的 API；后续“学习”也只能是只读参考 + 实践后提炼。

## 知识卡片模板（业界实践）

所有知识（频道知识、任务知识、个人知识、lessons）统一用一张 **Markdown 知识卡**，而不是裸字段。机器元数据放 frontmatter/DB 列，正文按“先结论、后细节”的人类阅读顺序组织。

### 元数据（机器 + 快速扫描）

```yaml
title: 一句话结论（≤80 字，一个卡片只表达一个主张）
type: convention | decision | workflow | role_requirement | insight | task_finding | personal_lesson
scope: global | channel | task | role
authority: normative | reference        # 仅 convention 可为 normative
status: draft | proposed | approved | rejected | deprecated | expired
owner: 角色/human
source_task / source_run: 来源
review_at / expires_at: 复核/失效时间
tags / repo / related / supersedes / conflicts
```

### 正文模板

```markdown
# <一句话结论>

> **TL;DR**：<1–2 句，人先读这一句就能判断是否相关>

## 适用范围
- 何时适用（Given / When）：
- 何时不适用（Exceptions）：

## 知识主体
- 约定：必须 / 禁止 / 应该 …
- 决策：决定做什么 + 备选方案
- 流程：步骤 1…N（每步动作 + 预期结果）
- 经验：观察 + 结论

## 理由与证据
- 为什么：
- 证据 / 来源任务 / 指标：
- 备选方案与取舍：

## 如何执行与验证
- 执行方式：
- 验证方法 / 检查清单：
- 已知失败模式：

## 示例
- ✅ 正确：
- ❌ 错误：

## 关联
- 取代 / 冲突 / 相关卡片：

## 复核
- Owner / 批准人 / 复核日期 / 版本历史
```

### 类型化必填项

| Type | 必填正文 |
|---|---|
| `convention` | 规则、适用范围、理由、示例、验证方法、例外 |
| `decision` | 背景、决定、备选方案、后果/取舍、状态（ADR 结构） |
| `workflow` | 目的、前置条件、步骤、验证、回滚/失败处理（SOP/runbook） |
| `role_requirement` | 能力、为什么需要、何时需要、证据、替代方案 |
| `insight` | 观察、证据、结论、适用性、反例（postmortem/lessons learned） |
| `task_finding` | 任务上下文、发现、验证方式、可复用范围 |
| `personal_lesson` | 实践任务/run、结果、提炼出的经验、适用性、置信度 |

### 校验与写作规则

- 标题 ≤80 字、TL;DR ≤200 字、正文 ≤4000 字；一个卡片一个主张（Zettelkasten 原子性）。
- `normative convention` 必须有示例、验证方法、例外，否则不能批准。
- 收割知识必须有 `source_task` 且任务终态；个人知识必须有成功实践证据。
- 适用范围与验证尽量用 Given/When/Then，便于评审时机械检查。
- 正文用中文人类可读标签；前端用表单生成 Markdown，列表只显示标题 + TL;DR + 类型/约束力/状态徽章。
- 参考实践：ADR（Nygard）、SOP/runbook、规则卡（Rule/Rationale/Examples/Exceptions）、复盘/lessons learned、Zettelkasten 原子笔记、Diátaxis 文档分类、docs-as-code、SECI（实践→外化→组合→内化）、渐进披露。

## 决策与范围

**做：**

1. 保留 `workspaces` 表/API/页面与 `workspace_id`；新增 `workspaces.knowledge_repo`。频道保留单一 `repo`（默认/领域 repo）；频道是任务的上一层抽象，任务 `repo` 可不同；不引入多 repo 容器。
2. 频道页面保留并扩展：概览、频道知识、资产、参与角色、设置；顶层建任务时选择频道并继承频道 repo（可显式改），子任务不可覆盖父任务结构标记。
3. 新增 `workspace_knowledge`：kind/authority/status/version/expiry/provenance；支持从已完成任务“收割”。
4. 新增 `task_knowledge`：任务参与角色共享；不是个人知识。
5. 个人知识写入加实践证据门控；notes/memories 增加 evidence/status 字段。
6. 频道约定绑定语义与显式标注；注入默认关闭，按试点指标再开启。
7. 任务归档：`done/closed` 可归档，Lobby 默认隐藏，独立归档页，支持批量/取消归档。
8. 任务大厅固定展示全部未归档任务，不做频道筛选；频道页新增「任务」页签，展示该频道全部任务（含已归档）；任务卡显示频道；任务详情显示频道与频道知识。
9. `workspace_members` 改为 `workspace_participants`（无 read/write/admin）；仅作自动派发偏好与页面展示，不硬限制 Cindy/claim。
10. **立即做**子任务 guardrail：Agent 只能建子任务、父任务参与校验、继承 workspace/repo/base_branch 且不可覆盖、知识回流父任务并打子任务标记。

**不做：**

- 频道消息/线程/DM；任务内结构化消息。
- 角色禁用/“禁用知识被引用”开关；`enabled` 不参与知识检索。
- role archetype/角色模板继承、直接导入其他角色 notes、自动把频道知识写进个人知识库。
- 自动知识归纳/自动任务摘要（后续版本）。
- RBAC/多用户权限；硬频道角色池。
- 版本号 v1.30.1（v1.30.0 之上包含 UI 反馈修正）。

## 1. 数据模型与迁移

### 1.1 表

- **保留 `workspaces`**：新增 `knowledge_repo TEXT`（频道知识 repo 名，可空）；`workspaces.repo` 保留为默认/领域 repo；不新增 `workspace_repos`。频道是任务的上一层抽象；顶层任务 `repo` 可不同，子任务继承父任务 repo 且不可覆盖。
- `workspace_members` → **`workspace_participants`**（workspace_id, role_slug, joined_at；**无 access**）；旧表改名 `_legacy_workspace_members`。参与角色仅作自动派发偏好/展示，不是权限。
- `tasks.workspace_id`、`board_drafts.workspace_id` 保持不变；新增 `tasks.archived_at TEXT`，索引 `(status, archived_at)`。
- 新增 `workspace_knowledge`：

```sql
CREATE TABLE IF NOT EXISTS workspace_knowledge (
  id            TEXT PRIMARY KEY,
  workspace_id  TEXT NOT NULL,
  repo          TEXT,                         -- knowledge repo 名
  kind          TEXT NOT NULL,                -- convention|workflow|role_requirement|decision|insight
  authority     TEXT NOT NULL DEFAULT 'reference', -- normative|reference
  title         TEXT NOT NULL,
  tldr          TEXT NOT NULL,
  body_md       TEXT NOT NULL,
  fields_json   TEXT NOT NULL DEFAULT '{}',
  tags_json     TEXT NOT NULL DEFAULT '[]',
  source_task_id TEXT,
  source_subtask_id TEXT,
  source_knowledge_json TEXT NOT NULL DEFAULT '[]',
  owner         TEXT,
  related_json  TEXT NOT NULL DEFAULT '[]',
  supersedes_id TEXT,
  content_hash  TEXT,
  status        TEXT NOT NULL DEFAULT 'proposed', -- draft|proposed|approved|rejected|deprecated|expired
  version       INTEGER NOT NULL DEFAULT 1,
  created_by    TEXT,
  origin        TEXT NOT NULL DEFAULT 'human', -- human|agent|system
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  approved_at   TEXT,
  approved_by   TEXT,
  expires_at    TEXT,
  last_hit_at   TEXT,
  hit_count     INTEGER NOT NULL DEFAULT 0,
  review_at     TEXT,
  conflicts_json TEXT NOT NULL DEFAULT '[]',
  completeness  REAL NOT NULL DEFAULT 0,
  template_version INTEGER NOT NULL DEFAULT 1
);
```

- 幂等唯一索引：`workspace_knowledge(workspace_id, source_task_id, kind, content_hash) WHERE source_task_id IS NOT NULL`，防止同一任务重复收割。
- 新增 `workspace_knowledge_versions`（knowledge_id, version, title, tldr, body_md, fields_json, authority, status, source_task_id, source_subtask_id, origin, created_at, created_by）；每次创建/更新追加快照；**已批准卡片不可原地改，修改即生成新版本/新 proposal**。
- `hit_count` 注入时累加；`review_at` 触发复盘；`conflicts_json` 记录冲突卡片 id；`completeness` 为模板完整度；`template_version` 用于模板升级。
- 新增 `workspace_knowledge_fts` / `task_knowledge_fts`（仿 `notes_fts` trigram + 触发器），用于关键词检索。
- 新增 `task_knowledge`：id, task_id, parent_task_id, source_subtask_id, origin(task|subtask), kind, title, tldr, body_md, fields_json, tags_json, source_role, status(active/archived), created_at, updated_at；索引 `(task_id, status)`、`(parent_task_id, status)`。
- `notes`/`lessons` 采用同一卡片的紧凑版：新增 `title`, `tldr`, `fields_json`；现有 `content` 作为正文（不改列名）；旧数据迁移时 `title`=首行、`tldr`=前 200 字。`memories` 同样支持紧凑卡片字段。
- 个人知识证据：`notes` 增加 `practice_task_id`, `practice_run_id`, `outcome`, `verified_at`, `status(draft|active)`, `source_knowledge_json`；`memories` 增加同样字段（或新增 `knowledge_writes` 审计表）。CIC/检索默认只取 `status='active'`。
- 不新增 role_archives / role_templates / project_roles / project_context。

### 1.2 迁移

在 `db.py` 的 `init_schema` 后新增 `_migrate_channel_knowledge_v1(conn)`，沿用 `_setting` marker：

1. `workspaces` 补 `knowledge_repo`；`tasks` 补 `archived_at`；`tasks`/`board_drafts` 保持 `workspace_id`。
2. `workspace_members` 复制到 `workspace_participants`，**丢弃 access**；旧表改名 `_legacy_workspace_members`。
3. `notes`/`lessons`/`memories` 补 `title/tldr/fields_json` 与证据字段；已有行 `status='active'`、证据为空；旧 `title`=首行、`tldr`=前 200 字。
4. 新表、版本表、FTS 表、索引在 ALTER 之后创建。
5. `BEGIN IMMEDIATE` + marker 保证幂等；失败回滚。

## 2. 后端服务与 API

### 2.1 频道

- `services/workspace.py` 保留并扩展：CRUD、`knowledge_repo`、`tree/diff` 默认从频道 repo 解析，也接受显式 `repo` 参数。
- `api/workspaces.py` 保留 `/workspaces`；旧 `/members` 端点保留一个版本作为 participants 别名，忽略 `access`。
- 删除频道：任务 `workspace_id=NULL`，不删任务；`workspace_participants`/`workspace_knowledge` 删除；保留 `source_task_id` 历史指针。

### 2.2 频道知识

- `services/knowledge_card.py`（新）：统一卡片模板、类型化必填校验、Markdown 渲染/解析；workspace/task/notes/lessons 共用。
- `services/workspace_knowledge.py`：
  - `create/update/list/get/approve/reject/delete`。
  - human 写入 → `approved`；Agent 写入 → `proposed`；approve/reject 仅 human。
  - `version` 递增 + `workspace_knowledge_versions` 快照；`expires_at` 过期不注入；`last_hit_at`/`hit_count` 注入时更新。
  - 创建时 `kind=convention` 默认 `authority=normative`，其余默认 `reference`；human 可显式改。
  - `render_for_task(task, bound)`：绑定频道 → convention 标“约束”；只引用 repo → 全部标“参考”。
  - **从任务收割**：`harvest_from_task(workspace_id, task_id, items, actor)`；任务必须 `done/closed` 且属于该频道；系统/Agent 生成 `proposed`，human 手动收割可直接 `approved`；记录 `source_task_id` + `source_subtask_id`。
- API：`GET/POST /workspaces/{id}/knowledge`、`PATCH/DELETE /workspaces/{id}/knowledge/{kid}`、`POST .../approve|reject`、`POST /workspaces/{id}/knowledge/harvest`；对已批准卡的 PATCH 生成新 proposal/version，不原地改；DELETE 仅 human（建议用 deprecate）。
- 入参统一为 `{title, tldr, kind, authority, fields, tags, source_task_id, source_subtask_id, owner, review_at, expires_at, related, supersedes_id}`；`body_md` 由 `knowledge_card.render(fields)` 生成，也允许直接传 Markdown。
- knowledge repo 跨频道引用：任务通过现有 `task_knowledge_repos` 绑定 repo；`workspace_knowledge` 按 `repo` 检索；是否绑定频道由 `tasks.workspace_id` 判定。

#### 2.2.1 知识收割与审批矩阵

| 知识层级 | 谁写入 | 谁批准 | 默认状态 |
|---|---|---|---|
| **任务知识** | 任务参与角色 / human | 无需预审批（任务内共享） | `active` |
| **个人知识** | 角色（带成功实践证据）/ human | 无需预审批；human 可审计、可 force | 有证据 `active`，无证据 `draft` |
| **频道知识（人工）** | human | human | `approved` |
| **频道知识（Agent/Cindy）** | Agent 只能 propose | **human** | `proposed` |
| **频道知识（任务收割草稿）** | 任务 `done/closed` 后由 human/Agent 触发收割，系统确定性生成 | **human** | `proposed` |
| **Global lessons** | 任意角色 propose | human | `pending → approved`（现有） |

规则：

- **从任务收割到频道**：只允许终态任务且属于该频道；系统/角色生成 `proposed` 草稿，human 在频道页或收件箱确认后才 `approved`。
- **normative convention 必须 human 批准**；`CHANNEL_KNOWLEDGE_AGENT_AUTO_APPROVE` 默认 0，不允许 Agent 自批。
- **任务知识不需要 human 预审批**；任务结束只读/归档，human 可删除。
- **个人知识不需要 human 预审批**，但必须带成功实践证据；human 可强制写入/删除。
- Cindy 可以提出频道 workflow/role_requirement 更新建议，但不能批准，也不限制 Cindy 的任务规划。

#### 2.2.2 价值判断与淘汰

- **最终判断人：human**。系统不自动判定“无收益/误导”，只提供证据和提醒。
- 系统信号：
  - `last_hit_at` / 命中次数、被引用次数；
  - 使用该知识的任务 vs 未使用任务：评审驳回率、返工次数、任务周期、token 成本；
  - 过期、重复、冲突、低命中标记；
  - 试点开关（按频道开/关）对比。
- 周期复盘：每周或每 N 个任务生成「频道知识复盘」收件箱项/提醒，列出低命中、过期、冲突、长期未更新的条目；human 决定保留/更新/归档/删除。
- 自动动作只做“排除注入”（过期/未批准/冲突未解决），**不自动删除 approved 条目**；淘汰必须 human 操作。
- Agent 可以提交“该约定与任务结果冲突”的 proposal/flag，但不能自主删除或改写。

#### 2.2.3 并发与冲突

- **v1.30 简化方案：已批准知识卡不可原地修改**。任何编辑都生成新版本 / 新 proposal，当前 approved 版本保持不变；Agent 之间主要在“新增提案”上并发，只有状态流转使用 `expected_version`。
- 每条知识有 `version` + `updated_at`；更新、审批、拒绝必须带 `expected_version`（或 `If-Match`）；不匹配返回 409 + 当前内容。
- 状态变更用条件更新：`UPDATE ... SET version=version+1, status=? WHERE id=? AND version=?`；`rowcount=0` → 409。
- `BEGIN IMMEDIATE` 包住“条目更新 + version 快照 + FTS 更新”；失败回滚。
- **收割幂等**：唯一键 `(workspace_id, source_task_id, kind, content_hash)`；重复收割返回已有草稿，不重复插入。
- **重复/冲突检测**：创建/审批时用 token 重叠 + 4-char shingle/Jaccard（复用 `knowledge._rank`）找相似/矛盾条目；提示 human，需显式确认才可继续；不自动合并。
- **个人 notes**：`replace` 带 `expected_hash`，不匹配 409；`append` 在 `BEGIN IMMEDIATE` 中重读后追加；MEMORY.md 只由 active 写入，draft 不落文件。
- 注入读取只取 approved/active；`last_hit_at` 批量/低频更新，避免与审批写锁竞争。
- UI：统一 `useKnowledgeMutation` hook：自动带 `expected_version`、捕获 409、拉取最新版本、展示差异；提供“重新加载 / 保存为新提案 / human 强制覆盖”。
- Agent/CLI 提供 `--expected-version`；409 时返回当前版本，Agent 可重试或转为 proposal；Agent 不允许 force。
- 事务内不做 LLM 调用；`last_hit_at`/`hit_count` 批量、低频更新；收割幂等。

#### 2.2.4 知识卡的可维护性：渐进披露与校验

- **两级模板**：
  - `proposal`（draft/proposed）最小必填：title、kind、scope、TL;DR、一句话主体、source_task/owner；其余可空。
  - `approved`（尤其 normative/收割）完整必填：按 kind 的类型化必填项；不满足不能 approve。
- **渐进披露**：编辑器按 kind 只显示相关字段，分“核心 / 建议 / 可选”三组，高级项默认折叠；列表只显示标题 + TL;DR + 徽章。
- **完整度与校验分级**：
  - `completeness` 0–100，按字段权重计算，列表显示进度条。
  - `error`：阻止 approve（如 normative convention 缺示例/验证/例外）。
  - `warning`：允许但标记（如“尽量/适当”等模糊词、缺反例、缺来源）。
  - `info`：建议（如可补充关联卡片）。
- **模板辅助**：
  - `GET /knowledge/card/template?kind=...` 返回字段 schema + 示例。
  - `POST /knowledge/card/validate` 只校验不落库；前端实时调用。
  - CLI `anvil knowledge card template --kind` / `validate` 供 Agent 使用。
  - “从任务摘要预填”：收割时自动填 title/TL;DR/主体/来源，human 只补理由/示例/例外。
- **质量 lint**：模糊词检测、重复/近似卡检测、normative 规则缺示例、decision 缺备选、workflow 缺回滚 → warning/error。
- **模板版本**：`template_version` 记录；升级时旧卡保留，approve 时按当前模板校验；不做批量重写。
- **避免形式主义**：reference/低风险卡允许最小模板；只有 normative/被注入的卡要求完整；人工可“一键降级为参考”以减少必填负担。

#### 2.2.5 知识老化与冲突消解

- **新鲜度分数**（只用于排序/复盘，不自动删除）：
  - `freshness = 0.4 * exp(-age_days / 90) + 0.25 * log(1 + hit_count) + 0.2 * outcome_signal + 0.15 * completeness`
  - `outcome_signal` 来自使用该卡的任务评审/返工/周期；参考 Generative Agents 的 recency/relevance/importance、MemoryBank 的遗忘曲线、IER 的经验淘汰。
- **复核周期**：
  - convention 90 天、decision 180 天、workflow 180 天、insight 365 天；`review_at` 到期进入「知识复盘」收件箱。
  - `expires_at` 过期只排除注入，卡片仍可搜索并标“已过期”。
- **冲突检测**：
  - 重复：content hash + 4-char shingle/Jaccard（复用 `knowledge._rank`）。
  - 矛盾：同 scope/kind/tags 且高重叠，但出现相反模态（必须/禁止、启用/弃用）；v1.30 用规则/模态词标记，human 裁决；LLM/embedding 矛盾检测留到 v1.32。
  - 取代：`supersedes_id` 指向旧卡，旧卡标 `deprecated`，保留历史。
  - 冲突写入 `conflicts_json`；UI 显示“与 X 冲突”，未解决前不注入。
- **低价值淘汰**：
  - 连续 N 个任务未命中、review 到期未确认、冲突未解决 → 进入“待归档”候选；human 选择续期/更新/归档/删除。
  - 归档保留搜索与来源；不物理删除 approved 卡片，除非 human 明确删除。
- **自动动作边界**：只做“排除注入/排序降权/生成复盘项”，不自动 approve/reject/delete；所有淘汰由 human 确认。
- **后续增强**：v1.31 自动归纳提案 + 冲突合并建议；v1.32 embedding/图谱矛盾检测。

#### 2.5.1 角色创建子任务（已实现，需补 guardrail）

现状核对：

- `POST /tasks` 使用 `get_auth`，Agent 可以创建任务；`anvil task create --parent` 已存在；`tasks.create` 在 `parent_id` 下继承父任务的 repo/workspace/base_branch。
- 因此“角色自己决定是否创建子任务”的能力已经存在，但缺约束：目前 Agent 也能创建顶层任务、在任意父任务下创建、跨 workspace 创建。

规则：

- Agent **只能创建子任务**（`parent_id` 必填）；顶层任务保持 human 创建。
- 父任务必须存在，且 Agent 必须是父任务的 assignee/参与角色；否则 409。
- 子任务**从属于父任务**：继承父任务的 `workspace_id`、`repo`、`base_branch`，**不允许覆盖**；请求里显式传入不同值 → 409。子任务可以有独立的 title/description/scope_paths/assignees/tags，但不得改变父任务的结构标记。
- 该规则对 human 创建的子任务同样生效；human 如需换 repo/workspace，应新建顶层任务或先调整父任务。
- `created_by=agent:<role>`，写 audit；Cindy/planner 仍走 board draft + human 审批，不直接建任务。
- 测试：Agent 可在自己参与的任务下创建子任务；不能建顶层；不能在他人的任务下建；不能覆盖 workspace/repo/base_branch；审计记录。

10. 角色在自己的任务下用 `anvil task create --parent` 创建子任务 → 出现在任务详情；尝试创建顶层或在他人的任务下创建 → 403/409；尝试覆盖 repo/base_branch → 409；子任务写入知识 → 父任务知识视图显示“来自子任务”；收割到频道记录 source_subtask_id。
11. 新建 normative convention 缺示例/验证/例外 → 不能 approve；补全后通过，completeness 显示 100%。
12. 两个窗口同时编辑同一卡 → 后提交者 409，显示差异；选择“保存为新提案”生成新版本，approved 版本不变。
13. 过期/待复核/冲突条目出现在「知识复盘」；过期条目不注入 CIC，human 续期/归档后恢复或移除。

## 附录 A：与业界频道/知识管理架构对比（存档）

### A.1 对比口径：Anvil 整体实现 vs 多 Agent 项目

Anvil 的整体实现：

- **交互场所**：任务时间线（`activities + events + audit`），不是频道。
- **工作单元**：任务板/任务大厅 + 任务详情；`task` 是唯一执行单元。
- **编排**：Cindy 规划 + workflow DAG + step contract + review gate；`@mention` 作为动态补充。
- **角色**：常驻角色 runtime + 每角色每任务上下文槽 + Agent Inbox。
- **人类**：单用户 + HITL（review/gate/decision/action card）。
- **知识**：role notes/MEMORY、task snapshot、repo lessons、任务知识仓库绑定。
- **执行**：workspace/repo + worktree；SSE；审计与回放。

对比方法：不看单个功能名，而看每个项目把 **Agent 交互场所、任务单元、编排/路由、知识/记忆、人类角色** 放在哪一层，再映射到 Anvil 的对应层。频道只是其中一种落点。

对标对象：

- 协作会话型：Raft、Poco、OpenCrew、AgentRQ、LIT、Mantle。
- 群聊/组织型：AgentTeams（Matrix）、Claude Tag。
- 任务内会话型：AutoGen GroupChat；SOP/角色型：MetaGPT、ChatDev。
- 集成型：Qwen Code Channels（外部 IM → Agent 任务）。
- 知识管理：ADR/RFC/SOP/Postmortem、Confluence/Notion/Obsidian、MemGPT/Mem0/MemoryOS、G-Memory、AWM/ExpeL/ECL/IER/MAEL/Voyager、GraphRAG/HippoRAG。

### A.2 各项目功能落点 → Anvil 对应实现

| 项目 | Agent 交互/频道场所 | 任务/工作单元 | 编排/路由 | 知识/记忆 | Anvil 对应实现 | 主要差异 |
|---|---|---|---|---|---|---|
| Raft | channel + thread + DM；Agent 是一等成员 | task board + thread | @mention/涌现式协作 | 频道历史 + thread | 任务时间线 + 任务板 + Cindy/workflow + 角色 notes | Anvil 把交互落在任务层；没有频道/thread/DM 的 ambient 协作 |
| Poco | channel/DM 对话空间 | 消息转 task，绑定来源 thread | 对话驱动 | 频道上下文 + shared files | 手工建任务 + 任务时间线 + 任务知识/频道 repo | 没有“先对话、后任务”和消息→任务 |

| AutoGen GroupChat | 任务内单一共享会话 | 会话即任务 | speaker selection | 共享 conversation | 任务时间线 + workflow | 同为任务内共享；Anvil 多了常驻角色/HITL/审计 |
| MetaGPT/ChatDev | 无频道；SOP/chat chain | SOP 流水线 | 角色分工/阶段 | 共享消息池/产物 | workflow DAG + step contract + review gate | Anvil 是运行期编排；它们多是一次性流水线 |

结论：

- Raft/Poco/OpenCrew/AgentRQ/LIT/Mantle 把 Agent 交互房间放在 **channel/thread 层**；Anvil 放在 **task 层**。
- AgentTeams/Claude Tag 放在 **组织/群聊层**；AutoGen 放在 **任务内会话层**；MetaGPT/ChatDev 放在 **SOP/角色层**。
- Anvil 的整体形态是 **task-as-channel + 集中式 SOP + 常驻角色 + HITL + 本地单用户**。本方案新增的频道层只承担 **跨任务知识作用域 + 任务归属 + 资产**，不补聊天房间。
- 因此与 Raft/Poco 相比，Anvil 少了预任务讨论/消息转任务/ambient；与 MetaGPT/ChatDev 相比，Anvil 多了运行期编排与 HITL；与 AutoGen 相比，Anvil 多了常驻角色、审计与治理。

### A.5 本方案优点

1. **不重复造聊天层**：任务会话继续承担多 Agent 协作；频道只做任务归属、知识 repo、资产，避免 Raft/Poco 式“频道消息 vs 任务时间线”双状态源。
2. **作用域与约束力清晰**：global/channel/task/role 四层；频道约定对绑定任务 normative，对只引用 repo 的任务 reference，显式标记。
3. **个人知识质量优先**：只读理解 + 成功实践 + 提炼，避免盲抄、跨角色污染、未经验证的知识进入上下文。
4. **人类可读**：统一知识卡模板（ADR/SOP/规则卡/复盘/Zettelkasten），审批者看的是卡片，不是 JSON 字段。
5. **治理完整**：Agent 只能 propose，human 审批频道知识；版本、过期、冲突检测、并发控制、复盘提醒。
6. **增量落地**：复用 `workspaces`、`task_knowledge_repos`、`notes/lessons`、任务时间线；不需要重写平台。
7. **跨频道复用**：频道 knowledge repo 可被其他任务绑定；只读参考，不直接变成个人知识。
8. **任务归档**解决任务过多，不引入项目归档/多级导航。

从整体架构对比看：与 Raft/Poco 相比，Anvil 用任务时间线替代 channel/thread，避免了“频道消息 vs 任务时间线”双状态源，但放弃了消息转任务和预任务讨论；与 AutoGen 相比同为任务级共享会话，Anvil 多了常驻角色、HITL、审计；与 MetaGPT/ChatDev 相比，Anvil 是运行期编排而非一次性 SOP 流水线，HITL/恢复更强。

### A.6 本方案缺点/风险

1. **手工整理负担**：频道知识需要 human 审批与维护；如果用户不投入，知识库会空转。v1.30 用最小 proposal、任务摘要预填、复盘提醒降低负担，但仍需 human 参与。
2. **自动累积缺失**：相比 AWM/ECL/IER，v1.30 不自动归纳 workflow/经验；价值依赖人工纪律。
3. **语义检索弱**：仅 FTS + 标签/时间，跨表述召回不如 GraphRAG/向量检索。
4. **频道知识价值未验证**：约定/workflow 注入默认关闭；必须用试点指标决定是否开启。
5. **无预任务/跨任务聊天**：相比 Raft/Poco/AgentTeams，缺少任务产生前的讨论空间；主任务人工创建、子任务由角色运行时自己创建（不是消息驱动），子任务继承父任务结构标记且不可覆盖，知识回流父任务并打子任务标记；这是有意的任务派生模型，但需要 guardrail。
6. **角色知识在 v1.30 仍偏孤岛**：只能只读参考（后续）+ 实践提炼，跨角色学习效率低于 MAEL/G-Memory。
7. **实践门控可能过严**：task/run 证据缺失时只能写 draft；需要 human force 和良好 UX，否则角色会少写知识。
8. **知识卡模板有维护成本**：类型化必填项多，可能变成形式主义。v1.30 已给方案：proposal 最小必填、approved 分级校验、completeness、模板辅助/预填、可降级为 reference。
9. **并发/版本增加复杂度**：单用户下 UI 与多个 Agent 仍可能竞争。v1.30 已给方案：approved 卡不可变、编辑即新 proposal、统一 `useKnowledgeMutation`、Agent 只新增提案。
10. **迁移与兼容**：participants/access、notes/lessons 字段、FTS 表都需要迁移；旧脚本依赖 `access` 的行为会变化。
11. **无多用户/RBAC/组织建模**：不适合团队协作或对 Agent 做严格权限隔离。
12. **淘汰仍靠人工**：过期只排除注入，不自动清理；知识库可能随时间膨胀。v1.30 已给方案：freshness 排序、`review_at` 复盘、低命中待归档、冲突检测；仍由 human 决定，不自动删除。

这些缺口的共同原因是 Anvil 把 channel/thread 的能力压缩到了任务层：单用户、任务级隔离换来了可审计与低复杂度，但失去了频道层的 ambient、任务派生和多人组织能力。本方案只补“跨任务知识”，不试图补回整层频道协作。

### A.7 差距与后续版本

| 差距 | 后续版本建议 |
|---|---|
| 自动归纳 workflow/约定/经验 | v1.31：任务完成后生成 proposed 知识卡（AWM/ECL/IER 思路），human 批准 + 淘汰 |
| 语义/图检索 | v1.32：embedding/GraphRAG/G-Memory 式检索；先离线评估召回 |
| 角色知识只读参考 | 后续：把角色知识作为只读 knowledge repo 暴露；仍不允许直接导入 |
| 角色删除归档/学习 | 后续：archive/keep/delete + role_archives；学习只能实践后提炼 |
| 预任务/跨任务频道聊天 | 仅当多用户/ambient 协作成为目标时引入；否则坚持任务即协作面 |
| 多用户/RBAC | 若转向团队产品，需要重新设计频道成员/可见性/审批流 |

### A.8 决策建议

- **如果目标是单机单用户、可审计、可治理的多 Agent 知识作用域**：本方案匹配度高；先做 v1.30 基座，频道知识注入默认关闭，用试点指标决定是否启用。
- **如果目标是最大化自动复用/减少人工**：应把 AWM/ECL/IER 式自动归纳提前到 v1.30 或紧随其后。
- **如果目标是多人/团队协作**：本方案不够，需要补频道消息/线程、成员可见性、RBAC、通知；届时可参考 Raft/Poco/AgentTeams，但要避免与任务会话重复。
- **如果目标是纯任务执行、不需要跨任务知识**：可以只做任务归档 + 任务会话，频道知识作用域延后。
