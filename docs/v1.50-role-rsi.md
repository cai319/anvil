## Context

Anvil 已有完整的角色、任务/工作流、知识审批与 HITL 基础，但角色演化仍停留在
「低风险字段自主改、中风险人工批、高风险禁止」的静态分权（`design.md` 第九章）。
该章明确否决过无人值守演化，理由是：**提示词缓慢漂移、个人样本量不足、退化难以察觉**。
v1.50 不是简单推翻，而是把当时的否决条件逐个解决：

- **画像分层**：Charter（宪章，只读/只提案）与 Strategy（策略，可演化但人工晋级）分离，
  防止身份漂移；
- **证据与统计**：每任务完成回执 + 隐藏回放集（held-in/held-out）+ 配对统计 +
  噪声门槛 + 显式 `inconclusive`，解决样本量与退化检测；
- **可审计可回滚**：版本快照、SOAKING 观察窗、漂移监控、人工晋级、负结果归档；
- **边界分离**：角色自身可改的部件由 RSI 处理；运行时加载的部件（skill/MCP/CLI/YAML/
  权限等）只生成给 human 的方案 md，角色永不直接改运行时。

实施方式（SDD/TDD）：
1. **本文档**：设计背景、决策与算法依据，归档在 `docs/v1.50-role-rsi.md`
   （加入 `.gitignore`，本地内部设计文档，不随仓库发布）；
2. **Spec**：`docs/superpowers/specs/2026-11-24-anvil-role-rsi-spec.md`
   （需求 ID、Given/When/Then 验收、契约、测试矩阵；Spec 是实施唯一真相源）；
3. **TDD 实施**：按 §11 的 SDD/TDD 规范，逐阶段“先写失败测试 → 最小实现 → 重构 →
   全量回归”；后端 pytest 必须全绿，前端 `npm run build` + CDP 手测；
4. **发布**：全部阶段通过 P6 验收后，汇总 release note；**版本号与 commit 前先与用户
   确认**（遵循本机提交规则），再打 v1.50.0。

已确认决策：
1. 角色空间权限三档：自主 / 人工审批 / 只提案；
2. 评估证据：在线任务信号 + 角色不可见的固定回放集（held-in/held-out、配对统计、
   证据不足输出 `inconclusive`），v1.50 不引入合成任务；
3. 运行时提案：应用内（DB/UI/CLI）为真相，md 生成到 `data/runtime-proposals/`，
   可导出到 `docs/runtime-proposals/` 供 human 实施；
4. 版本 = RSI 演进的角色空间快照；切换 = 读档；支持压缩 CAS + hash + 导出/导入。

## 0. 结论摘要

三个闭环，共用一个证据层；**观测/候选复用现有 `events` + `proposals`，只新增 2 个
持久状态家族**（`eval_runs`、`runtime_proposals`）：

```
任务 done / 评审驳回 / 步骤失败 / 返工
        │  （确定性、零 LLM）
        ▼
[rsi.observation 事件] ──► 触发策略（量/严重度/周期/预算）
        │
        ▼
[证据包 EvidenceBundle] ──► [角色反思 run] ──┬─► 知识收割（自主/审批/提案）
        ▲                                   ├─► 候选编辑 → proposals 归档
        │                                   └─► 运行时问题 → RIP md
        │
[评估算法] ◄── 隐藏回放集（隔离存储）+ 在线监控 + 人工锚点
        │  输出 fitness vector + diagnosis/direction
        ▼
[候选提案 proposals] ──► 人工晋级 ──► strategy version ──► SOAKING
        ▲                                                │
        └──── 漂移监控 / 自动回滚 / 负结果归档 ◄──────────┘
```

| 组件 | 核心机制 | 借鉴 |
|---|---|---|
| 1 角色 RSI | 每任务回执 → 失败签名聚类 → 有界候选 → held-in/held-out 门控 → Pareto 归档 → 人工晋级 → SOAKING | Self-Harness、AHE、GEPA、DGM、Meta-Harness、MCE、ACE |
| 2 评估算法 | 角色 episode 归因、确定性 verifier 优先、隐藏回放、配对 bootstrap、噪声门槛、`inconclusive`、judge 校准、漂移监控 | Self-Harness、AHE、DGM、GEPA、ACE、Weng 2026 |
| 3 运行时提案 | 确定性检测 + 组件分类 + 签名去重 + RIP md + 应用内生命周期 + human 独占流转 | AHE 的组件边界 + Anvil 现有 HITL |

## 1. 概念与不变量

### 1.1 角色画像 = Charter（宪章）+ Strategy（策略）+ Experience（经验）

| 层 | 内容 | 权限 | 是否总是注入 |
|---|---|---|---|
| **Charter 宪章** | `definition_json` + `role_tools` + runtime 绑定：`display_name`、`description`（仅供人看）、`system_prompt`、`working_mode`、`skill_description`、`responsibilities`、`capabilities`、`runtime`、`workspace`、`tools`、`skills/MCP`、`concurrency` | **只读/只提案**；只能走现有 `proposals` / `role_suggestion`，人工批准 | 是（系统提示/职责/能力/tools） |
| **Strategy 策略** | `instruction.md` 的 `ANVIL:STRATEGY` 段、`PRINCIPLES.md`、`notes/playbooks/*`、受控的策展知识卡 | **人工审批**（例外见下） | 是（策略段/准则）；playbooks 索引 + 按需检索 |
| **Experience 经验** | 角色私有经验卡/notes（任务复盘产物） | **自主**（仍受实践门控与质量门） | 否，只按检索进入 |

`instruction.md` 用显式标记切分（缺失时整份视为 Charter，RSI 不得编辑）：

```md
<!-- ANVIL:CHARTER:BEGIN -->
（身份、使命、边界、不可做事项）
<!-- ANVIL:CHARTER:END -->
<!-- ANVIL:STRATEGY:BEGIN -->
（检查清单、领域套路、沟通模式、质量习惯）
<!-- ANVIL:STRATEGY:END -->
```

**硬不变量**（每次候选、每次晋级都校验）：
1. 不得改动 Charter 标记内内容、不得删除 `## 职责`、不得改写系统提示；
2. 不得引入权限/工具/运行时/模型变更（只能出现在提案/RIP 里）；
3. 每条候选编辑必须 `portrait_refs` 到真实职责/能力项，并附证据引用；
4. 不得包含“忽略人工审批 / 绕过评审 / 直接修改运行时 / 关闭测试”等指令；
5. 单次编辑与角色空间总量都有上限（§2.5）。
6. `charter_digest` CAS：候选创建时记录 digest；晋级时 digest 不一致 → 候选失效，
   必须重新反思。`charter_digest = sha256(canonical_json(charter fields) + "\n" +
   normalized_charter_block)`，由 `services/role_space.charter_digest()` 单写。

### 1.2 角色空间 RoleSpace

```
RoleSpace(role) = (Charter, Strategy, Experience)
```

- `Charter`：definition_json + role_tools + runtime 绑定（只读/只提案，见 §1.1）；
- `Strategy`：instruction 策略段、PRINCIPLES、playbooks；
- `Experience`：**所有角色私有知识**，包括
  - `notes/memory/cards/**`（经验卡）；
  - `notes/knowledge/**` 中 `scope=role` 的角色知识卡（vulnerability_pattern /
    failure_scenario / module_knowledge / decision / personal_lesson 等）；
    **排除 `task_snapshot` 与任务目录下的快照**（它们属于任务，不属于角色空间）；
  - `notes/playbooks/**`（若独立于 playbooks 目录）；
  - 每条卡的 ID、内容哈希、`origin`（human/rsi）、`source_cycle_id`、
    `source_role_version`；
- **不进入角色空间**：shared lessons、topic/channel/task knowledge、runtime proposals、
  日志/scratch/任务快照、`MEMORY.md` legacy；
- `profile.yaml` 仍是镜像，RSI 永不写它。

**版本完整性要求**：一个 evolution 版本必须覆盖**所有 RSI 可写产物**（Strategy +
Experience + 相关配置引用）。只快照 instruction 而漏掉角色知识卡，会导致切换后
“策略回退了、知识没回退”的半回退，必须避免。

### 1.2.1 工作集（Working Set）：每日知识是基线之上的增量

每日知识收割**不生成新版本**，而是写入 active evolution 版本之上的工作集：

```
WorkingSet(role) = (base_version, cards[{path,sha256,human_modified}], hash)
```

- `cards` = 当前 RSI 创建、但不在 active 版本 manifest 中的角色知识卡/playbook；
- `hash` 写入每次 run（`runs.working_set_hash`），因此一次 run 的真实上下文是
  **`(role_space_version, working_set_hash)`**，而不是只看版本号；
- 晋级时工作集被快照进新的 evolution 版本，工作集回到空；基线前移；
- 切换版本时，当前工作集由 `switch` 归档到 `notes/archive/switch-vN/`，目标版本从
  自己的快照开始，避免“旧版本 + 新知识”的错配；
- 评估必须分解而非相加：
  - 编辑效应：`(v, W, Δ)` vs `(v, W)`（同一工作集，隔离候选编辑）；
  - 知识效应：`(v, W)` vs `(v, W0)`（单独评估工作集增量）；
  - 最终报告 `ΔU = Δ_edit + Δ_working_set + 交互项`，分别展示，避免把工作集收益
    错误归因给版本，或把版本退化归因给知识。
- UI：版本行展示“基线 vN + M 张未版本化知识卡”；切换前提示工作集将归档。

**边界说明**：这里的“角色空间”是**单个角色的内部可迭代面**，不是角色组合/角色库。
新建角色、拆分角色、扩编团队仍走现有 `role_suggestion` / `role expand`（人工批准），
RSI 只在 `proposal` 档建议。

### 1.3 版本、归档与激活

- `role_versions` 只保存两类记录：`kind=evolution`（用户看到的“版本”=完整角色空间快照）
  与 `kind=config`（手动配置修订，默认隐藏）；**不再用 charter/strategy 两种版本**。
  - `evolution` 版本包含：Strategy/Experience 快照 + 当时的 `definition_json`（Charter）
    与 `role_tools` 引用 + `charter_digest`；切换时可按需完整恢复；
  - `config` 修订包含：手动改动的 definition/space 内容 + `content_hash`；默认不进入
    演进主视图，只用于审计/找回配置；
  - `status`：`candidate|active|archived|rejected|switched_out|deleted`；`config` 修订
    没有 `active`；
  - `parent_version`、`space_manifest_path/hash`、`charter_digest`、`eval_run_id`、
    `origin_candidate_id`、`promoted_at/by`、`note`、`content_hash`、`deleted_at`；
  - 不变量：每个 slug 至多一个 `kind=evolution AND status='active'`；active 由查询
    `ORDER BY version DESC LIMIT 1` 派生，不新增 `roles` 指针列（避免镜像状态）；
  - 历史行迁移为 `kind=config`（保留审计），不设 active；首次启用 RSI 时
    `ensure_baseline()` 用当前角色空间建 `kind=evolution, source=baseline`。
- 统一写路径：
  - `roles.update_profile` / `update_tools` / `update_catalog` 现在不写版本；v1.50 统一写
    `kind=config` 修订（content_hash 去重：同内容不新增，`coalesced_count` 记录合并次数），**不生成演进版本**；
  - 手动配置改变 `charter_digest`；RSI 候选创建时必须与 base digest 比对，不一致则
    重新 base 或拒绝；
  - `roles.rollback()` 现会先 `update` 再 `_snapshot_version` 产生两行；v1.50 改为：
    - evolution 版本 → `switch`（只改 active 指针）；
    - config 修订 → `restore-config`（显式、human、带 diff/warning）；
  - 现有 `POST /roles/{slug}/rollback/{version}` 保留兼容：按 kind 分派到上述动作。
- 快照目录：`data/agents/<slug>/.anvil/space-versions/v<N>/`
  - 只存 Strategy/Experience 可演化面 + `manifest.json`（相对路径、sha256、字符数、
    charter_digest）；Charter/tools 以 digest + 引用记录，不复制大文件；
  - 不存日志/scratch/任务快照；单文件 ≤64KB、单版本 ≤512KB，超限拒绝；
  - `diff.patch` 为 unified diff，供 UI/切换展示；
  - 历史 config 修订没有空间快照；首次启用 RSI 时建 `kind=evolution, source=baseline`。
- **通道收敛（防绕过）**：`role_rsi_lock_strategy` 开启时：
  - `POST /me/instruction`（`services/memory.write_instruction`）与
    `PUT /me/memory/principles` 只允许改 Strategy 段 / 追加准则，并转为 pending candidate
    （人工审批后生效）；
  - Charter 段、系统提示、职责等写入直接 403/422，并提示走 `anvil self propose`；
  - 经验卡、notes 仍自主（三档中的自主档）。
- 激活语义：策略晋级 = 原子写回快照文件 + 写 `role_versions(kind='evolution', status='active')`；
  运行中的 run 已有 frozen `profile_snapshot` 与已投影 `CLAUDE.md`，新版本从下一次 run
  生效；晋级时若角色有 running run，UI 提示“下一 run 生效”。

### 1.3.1 版本心智模型：版本 = RSI 演进的角色空间快照

**一句话：用户看到的“版本”就是角色在某个演进时刻的完整角色空间快照；当前版本 =
角色现在用的版本；切换版本 = 把角色恢复到那个快照**（例如用户觉得旧版本在项目中
效果更好）。

**版本里有什么（完整覆盖所有 RSI 改进）**：
- **Strategy**：`instruction.md` 的 Strategy 段、`PRINCIPLES.md`、`notes/playbooks/**`；
- **Experience / 角色知识**：`notes/memory/cards/**` 全部经验卡 +
  `notes/knowledge/**` 中 `scope=role` 的角色知识卡（含 ID、内容哈希、origin、
  source_cycle/source_role_version）；
- **Charter 引用**：当时的 `definition_json`（Charter）、`role_tools`、runtime 绑定、
  `charter_digest`（用于复现与 diff；默认切换只恢复 Strategy/Experience，
  完整恢复需显式选择）；
- **评估**：晋级前回放 verdict/Δ/CI + 该版本 active 期间的**实际运行表现**
  （success/rework/token/质量，带样本数）；
- **元数据**：`created_by`（rsi/human）、`source`（baseline/rsi/switch）、父版本、
  `content_hash`、diff、版本备注。

**不进入版本**：shared lessons、topic/channel/task knowledge、runtime proposals、
日志/scratch/任务快照、`MEMORY.md` legacy。RSI 对它们的改进走各自审批通道，
切换角色版本不会回退它们（UI 明确提示）。

**三种记录，不要混**：

| 记录 | 内容 | 默认 UI | 用途 |
|---|---|---|---|
| **演进版本** `kind=evolution` | RSI 基线/候选/晋级快照 | 是（“演进版本”主视图） | 切换、评估、审计、Pareto |
| **配置修订** `kind=config` | 手动改 profile/tools/catalog/instruction 等 | 否（折叠的“配置修订”页签） | 审计/找回配置，**不冒充演进** |
| **控制事件** `events` | switch/rollback/promote/reject | 时间线 | 审计 |

- 只有 `kind=evolution` 的版本出现在主版本列表和“切换”动作里；
- 手动配置改动不再生成“演进版本”，只写 `kind=config` 修订（content_hash 去重：同内容不新增，
  `coalesced_count` 记录合并次数），默认隐藏，可批量清理；这样 Cindy 600+ 的历史手动保存不会继续污染演进视图；
- 配置修订的 digest 使用 `charter_digest`（definition + role_tools + instruction Charter 段），
  因此 tools/catalog/instruction 的真实变化会产生不同 hash；重复保存同内容只累加
  `coalesced_count`，不再新增版本；
- 已有重复配置修订用“清理重复配置修订”按 content_hash 分组 soft delete，每组保留最新一条；
  不删不同内容的历史配置，保证可找回；
- 历史 `role_versions` 迁移为 `kind=config`（保留审计），人工预览后批量清理；
  第一次启用 RSI 时用当前角色空间建一个 `kind=evolution, source=baseline` 基线版本；
- **当前配置偏离提示**：若手动配置修订后当前角色空间与 active evolution 版本不一致，
  UI 显示“已偏离 vN”，提供“设为新基线”或“切换回 vN”；RSI 候选基于当前配置生成时，
  记录 `base_charter_digest` 并提示偏离。

**切换语义**：
- `POST /roles/{slug}/versions/{v}/switch`（human）：把该演进快照恢复到角色空间；
  被切换的版本置 `active`，原 active 置 `archived`；写 `rsi.version_switched` 事件；
  **不新增版本行**（版本号保持演进谱系，切换只是指针变化）；
- 默认只恢复 Strategy/Experience（RSI 可演化面）；若快照的 Charter digest 与当前不同，
  UI 显示 diff 并要求明确选择“仅恢复策略/经验”或“完整恢复（含 Charter/tools）”；
- 切换前若当前有未纳入任何演进版本的手动配置修订，提示“将丢弃未设基线的配置修订”；
- 切换后该版本成为“当前”，下一次 run 生效；正在运行的 run 继续用 frozen snapshot；
- **完整切换（含角色知识）**：切换按 manifest 恢复 Strategy 文件 + 角色知识卡；
  - 版本之后由 RSI 新建、但不在 manifest 中的卡：移到
    `notes/archive/switch-vN/`（不硬删，保留审计），避免“策略回退、知识没回退”；
  - `origin=human` 的卡：保留，不因切换删除；
  - RSI 创建但被 human 编辑过的卡：保留并提示“人工修改过，未归档”，版本状态标
    `partial_restore`；
  - 切换结果写入 `rsi.version_switched` 事件，记录 restored/archived/preserved 数量；
- UI 版本详情显示“包含 N 张角色知识卡 / N 个 playbook / 策略/准则”，切换前展示
  diff（文件 + 知识卡增删改）；
- “回滚”在 UI 中就是“切换回上一版本”，不需要单独的心智模型。
- **应用 vs 重新应用**：两者调用同一个 `switch`，只有目标版本不同；非 active 行叫
  “应用”，active 行叫“重新应用”。点击后先调用只读 `preview_switch`，展示文件
  added/modified/unchanged、知识卡恢复/归档/人工保留、Charter 差异与工作集，确认后
  才应用；不会重新跑评估。

**配置修订恢复语义（与演进切换分开）**：
- **基本信息页只做摘要**：显示当前演进版本、工作集、配置修订数量（不含 soft-deleted，
  单独显示“已清理 N 条”）与最近修订；
  不再直接列出数百条版本、也不再放“回退”按钮，避免把配置修订当演进版本。
- **所有版本操作收敛到演化页**：
  - `kind=evolution` 行 → “切换/重放” → `role_space.switch`，完整恢复 Strategy+Experience；
  - `kind=config` 行 → “恢复配置” → `role_space.restore_config`，恢复该修订的
    `definition_json`、manifest 中的 instruction/PRINCIPLES（若有）与 `role_tools_json`
    （若有）；不改变 active evolution 指针。
- 恢复前先 dry-run：返回将恢复的文件、是否恢复工具、警告；UI 弹窗明确告知
  “工具不会恢复”（legacy 修订无工具快照）或“仅 definition 可恢复”（无 manifest）。
- 恢复不新增版本行，写 `role.config_restored` 审计；旧
  `POST /roles/{slug}/rollback/{version}` 保留兼容，按 kind 分派到 switch/restore-config。
- 配置修订快照从 v1.50 起保存 `role_tools_json`，因此新修订可以完整恢复工具选择；
  历史修订只有 definition，恢复时给出 warning，不假装完整。

**RSI 标记与评分标记**：
- `RSI` 徽标：`kind=evolution` 且 `source in (rsi, rsi_candidate)`；`基线`、`手动` 分开；
- `当前` 徽标：`status=active`，列表置顶；
- **晋级前评分**：`eval_run_id` join `eval_runs` → `promote Δ+0.07 [0.02,0.12]` /
  `inconclusive` / `reject`；无评估显示“未评估”；
- **实际运行表现**：该版本 active 期间的任务指标（success/rework/token/质量，带样本数），
  由 `runs.role_space_version` 归属；这是用户判断“之前效果更好”的主要依据；
- 版本行可展开：预晋级评分 vs 实际表现、diff、证据、切换按钮。

**版本创建规则**：
1. 基线：首次启用 RSI 或人工“设为基线”；
2. RSI 候选：反思产出候选时建 `kind=evolution, status=candidate`；
3. RSI 晋级：评估+人工批准后 candidate → active；
4. 人工 switch/rollback：只改 active 指针，不新增行；
5. 手动配置修订：`kind=config`，content_hash 去重（同内容不新增，记录 coalesced_count），不进入演进主视图；
6. 版本号单调递增；主视图排序：当前 → 最近晋级 → 候选 → 归档；同组按时间倒序。

**筛选与批量删除**：
- 主视图筛选：source、status、是否有评分、verdict、实际成功率/返工、时间、关键词；
  服务端分页（默认 50/页），600+ 不一次性渲染；
- 批量删除：仅 human；**演进版本只能删 `archived/rejected` 且非 active/非 baseline/
  未被 active candidate/eval 引用**；配置修订单独批量清理；
- 删除动作：`status='deleted'` + `deleted_at`，删快照目录，写审计；物理 purge 二次确认；
- 快捷清理：`按 content_hash 去重`、`清理 90 天前配置修订`、`清理已拒绝候选`；
  全部 dry-run 预览数量与影响；
- Cindy 600+：上线时先迁移为 `config` 修订并预览重复项，人工确认后清理；之后手动保存
  不再进入演进主视图。

**“后续只要 RSI 持续演进”**：主视图默认就是“演进版本”；手动配置修订默认隐藏。P5 由
owner 决定是否进一步冻结手动策略编辑（人工改动先“设为基线”，再由 RSI 演进）；
该决策写入 §9.2。

### 1.3.2 版本存档格式：压缩 CAS + manifest hash 映射

**目标**：每个角色的每个版本都有可独立校验、可压缩、可去重的存档；切换前能验证
“这一版没坏”，删除后能回收空间。

**目录布局**：
```
data/agents/<slug>/.anvil/
├── space-cas/v1/<sha256>.z          # 内容寻址压缩 blob（zlib；小文件可 raw）
├── space-versions/v<N>/
│   ├── manifest.json                # 路径→hash/size/encoding/origin
│   ├── manifest.sha256              # canonical manifest 的哈希
│   └── archive.tar.zst              # 可选导出包（备份/迁移用，非运行时真相）
```

**manifest.json**（每个版本一份，DB 只存路径/hash）：
```json
{
  "schema_version": 1,
  "role": "backend-dev",
  "version": 13,
  "kind": "evolution",
  "source": "rsi_promote",
  "parent_version": 12,
  "created_at": "2026-11-24T...",
  "charter_digest": "sha256:...",
  "content_hash": "sha256:...",
  "files": [
    {"path":"instruction.md","sha256":"...","size":2048,
     "stored_sha256":"...","encoding":"zlib","compressed_size":900,
     "mode":"100644","origin":"rsi"}
  ],
  "knowledge_cards": [
    {"id":"N-...","path":"notes/knowledge/...","sha256":"...","origin":"rsi",
     "source_cycle":"RSI-...","source_role_version":13}
  ],
  "manifest_hash": "sha256(canonical(files + knowledge_cards + charter_digest))"
}
```

**hash 映射（三层）**：
1. **文件 hash**：`sha256(原始内容)`；压缩 blob 以原始 hash 命名，解压后重新 hash 校验；
2. **content_hash**：`sha256(canonical(files[].sha256 + knowledge_cards[].sha256 +
   charter_digest))`，不含时间/版本号，用于 no-op 判断与跨版本去重；
3. **manifest_hash / version_hash**：`sha256(canonical manifest)`，用于完整性看护；
   `manifest.sha256` 与 DB `space_manifest_hash` 双写，切换前比对。

**压缩策略**：
- 默认 `zlib`（Python 标准库，无新依赖）；文本/JSON/Markdown 通常 3–5×；
  压缩后不小于原文件 90% 时存 `raw`，避免小文件膨胀；
- 可选 `archive.tar.zst`（若环境有 zstd）用于导出/备份；运行时切换走 CAS，不依赖 tar；
- CAS 天然去重：未变化的知识卡/策略文件只存一份 blob，多个版本 manifest 引用同一 hash；
  删除版本后按 manifest 反向引用计数 GC 孤儿 blob（每周低峰，dry-run 可选）。

**完整性看护**：
- 创建版本：写文件 → 计算 hash → 写 manifest → `manifest.sha256` → fsync → 读回校验；
- 读取/切换前：校验 `manifest.sha256` → 逐文件解压并校验原始 hash → 全部通过才应用；
  任一失败 → 中止切换、标记 `integrity_status=corrupt`、通知人工；
- 周期校验：每周低峰 `verify_version` 扫描（可配），结果写 audit + `role_versions.
  integrity_status/last_verified_at`；
- UI 版本行显示短 hash（12 位）、文件数、压缩后大小、完整性状态；提供“验证”按钮；
- 损坏版本不自动删除，保留证据供人工处理。

**与 600+ 历史版本的迁移**：
- 历史 `role_versions` 只有 `definition_json`：迁移为 `kind=config`，按需（首次访问/
  清理预览）生成 `manifest.json` 并把 `definition.json` 压缩进 CAS；不阻塞启动；
- 批量清理时只需 manifest 的 hash/大小，无需解压全部内容；
- 新版本从第一天起统一走 CAS + manifest，避免再次出现“只有 DB 行、没有可校验存档”。

### 1.3.3 角色版本导出/导入（`<role>@v<N>`）

基于 §1.3.2 的 manifest/CAS，导出“某角色的某个版本”为可移植包；导入端校验后落地为
新角色或现有角色的新演进版本。

**包格式**：`role-<slug>-v<N>-<content_hash8>.anvil.zip`（ZIP/deflate，跨平台；可选
`tar.zst` 导出变体）：

```
export.json          # schema_version, anvil_version, exported_at, slug, display_name,
                     # version, kind, source, content_hash, manifest_hash, charter_digest,
                     # eval_summary, actual_performance, imported_from
manifest.json        # 同 §1.3.2：文件/知识卡路径、sha256、大小、origin
manifest.sha256
files/
  instruction.md
  PRINCIPLES.md
  playbooks/**
  notes/memory/cards/**
  notes/knowledge/**（仅 scope=role；排除 task_snapshot）
  charter.json       # definition_json + role_tools + runtime/model + skills/MCP 名称引用
README.md            # 人读摘要：角色/版本/评估/依赖/导入方式
```

**导出范围**：
- 包含：Strategy + Experience（角色知识）+ Charter/配置引用 + 评估与实际表现摘要；
- **不包含**：logs/scratch、任务快照、shared/topic/channel 知识、runtime proposals、
  eval suite/隐藏集、密钥/token、绝对路径、运行时 skill/MCP 的二进制或脚本内容
  （只保留名称引用，导入端重新解析）；
- 导出前可选脱敏扫描；包大小上限 20MB，超过拒绝并提示清理知识卡/归档。

**导入模式**（human-only）：
1. `new_role`（默认）：导入为新角色，slug 可指定（默认 `<原slug>-import-<hash4>`）；
   作为 `kind=evolution, source=import` 的基线版本；若本机缺 runtime/技能/MCP，
   角色以 `enabled=0` 落地并显示依赖报告，人工修复后再启用；
2. `add_version`：导入为现有同 slug 角色的新演进版本（不自动切换）；默认只导入
   Strategy/Experience，Charter 不一致时必须 `allow_charter_change=true` 并人工确认；
   导入后为 `candidate`/`archived`，人工预览 diff 再 switch；
3. 不支持“覆盖当前角色”模式；需要覆盖时走 `add_version` + 人工 switch。

**导入流水线**：
1. 上传到 `data/imports/<id>/` 隔离目录（0700，大小/zip-slip/符号链接校验）；
2. 校验 `manifest.sha256` + 逐文件 sha256；校验 schema/anvil 版本范围；
3. 解析 `export.json`，生成依赖报告（runtime/model/skills/MCP/playbook/知识卡 ID）；
4. 预览：文件/知识卡数量、Charter diff、缺失依赖、密钥扫描、版本冲突；
5. 人工确认 mode/slug/allow_charter_change；
6. 事务写入：新角色或新版本 + 恢复 Strategy/Experience + `content_hash`/`manifest_hash`
   + `source='import'` + `note='imported from <slug>@v<N>@<hash>'`；
   写 `role.imported` 审计；失败回滚；隔离目录清理；
7. 导入后不自动启用、不自动切换；新角色缺依赖时 `enabled=0`。

**安全**：
- 导入仅 `require_human`；agent token 403；
- ZIP 按不可信输入处理：路径穿越、绝对路径、符号链接、超大文件、可执行内容拒绝/隔离；
- 不含密钥；导入前扫描常见 token/私钥模式；
- 不导入运行时 skill/MCP 定义或 eval 数据；只接受名称引用，缺失项由人工映射；
- 所有 hash 校验失败即拒绝，不“尽力导入”。

**API / CLI / UI**：
- API：`GET /roles/{slug}/versions/{v}/export`（human，下载 zip）、
  `POST /roles/import/preview`（human，multipart）、`POST /roles/import`（human，
  mode/slug/confirm）、`GET /roles/imports/{id}`（状态）；
- CLI：`anvil role export <slug> --version <v> --out role.anvil.zip`、
  `anvil role import <file> --mode new --slug <new>`、
  `anvil role import --preview <file>`；
- UI：版本行“导出”；角色页“导入角色”按钮 → 预览弹窗（兼容性/依赖/Charter diff）→
  确认导入；导入版本显示 `导入` 徽标与来源；新角色缺依赖时显示待修复状态。

### 1.4 与 design.md 第九章否决的关系

| 当时否决理由 | v1.50 的解决 |
|---|---|
| 缓慢漂移、退化难察觉 | Charter/Strategy 分离；小 delta 编辑；版本快照 + diff；SOAKING 观察窗 + EWMA/CUSUM 漂移监控 + 一键/自动回滚 |
| 个人样本量不足 | 隐藏固定回放集（真实任务）+ held-in/held-out + 配对 bootstrap + 噪声门槛 + `inconclusive`；单任务不晋级 |
| 灰度对比不严谨 | 确定性 verifier 优先；rubric judge 固定 prompt/版本并人工锚点校准；A/A 噪声测量；成本/环境 pin |
| Agent 自我美化 | 反思与评估分离：角色只产出候选；评估器在循环外、只读、角色不可见；人工晋级 |
| 无法定位改坏点 | 候选关联 cycle/证据/预测；负结果归档；版本 diff + rollback |

### 1.5 完成契约：每个 done 任务都有回执

参与者 = `task_assignees` ∪ `tasks.assignee` ∪ 最新 workflow 的 `workflow_steps.role_slug`
∪ `task_role_claims.role_slug` ∪ `tasks.planner`；排除 `human/system/workflow` 与已删除角色。

每个 `done` 转换：

1. `rsi.observe_task_done(conn, task_id, source, actor)` 为每个参与者生成确定性证据摘要；
2. 写一条幂等 `events` 行 `rsi.observation`，唯一键
   `(source='rsi_observation', source_id=int64(sha1(role|task|completion_key)[:16]))`
   （现有 `events.source_id` 是 INTEGER，且已有 `UNIQUE(source, source_id)`，见
   `db.py:463-464`；用 64 位稳定哈希，冲突概率可忽略，命中冲突即幂等 no-op。
   `completion_key` 取本次完成身份：review 用 `audit.review` event id，dispatch 用
   `run_id`，workflow 用 `execution_no`——任务 reopen 后再次完成会产生新 observation）；
3. 写 `rsi.harvest_seed`，在达到触发条件时创建反思 run；
4. 角色可用 `anvil rsi retro --task <id> --file note.md` 补更丰富的复盘，写最多 2 条
   proposed 角色卡并记录 portrait refs；
5. 1 小时内没有 retro 回执 → 写 `rsi.harvest_deferred`，下一次反思补做；UI 显示
   “deferred”，不是“skipped”；
6. 任务完成路径永不被 RSI 阻塞；失败只记日志，由 scheduler 回填。

这满足“每一个任务完成时”都有确定性收割回执，同时把昂贵的模型反思做成批次。

### 1.6 三套独立上下文（任务 / RSI / 评估）

**结论：RSI 反思与评估必须各自独立 context，且都不能复用任务会话上下文。**
三者只在“版本快照”和“聚合 diagnosis”两个受控接口上交换信息，不共享会话、
不共享工作目录、不共享隐藏评测数据。

| 上下文 | 身份/载体 | 输入 | 绝不可见 | 生命周期 |
|---|---|---|---|---|
| **任务执行** | 角色，persistent task slot | 任务/步骤、任务知识、active Strategy/Experience | eval suite/item、verifier 命令、RSI 反思 transcript、evaluator 代码 | 按任务/切片；可 resume |
| **RSI 反思** | 角色身份，一次性 run，独立槽 `__rsi_reflect__` | 证据包、active Strategy、聚合 diagnosis、算子统计、负结果 | held-in/held-out item 内容与 ID、verifier 命令、evaluator 代码、任务会话 transcript | 每 cycle 新建，结束后销毁；**不 resume、不复用上一轮上下文** |
| **评估（L1 judge）** | 固定 evaluator 运行时/模型（`services/utility.generate`，临时目录） | 候选/基线 Strategy 快照、脱敏证据、rubric | 角色会话、角色 memory/notes、RSI 反思 transcript、真实角色 home | 每次调用无状态；不写角色空间 |
| **评估（L2 replay）** | 一次性 shadow 执行环境（shadow data dir + shadow role home） | 候选 Strategy/Experience 快照、item prompt、verifier（evaluator 执行） | 真实角色 home/notes、Anvil endpoint/token、隐藏集明文路径 | 每次 eval 新建，结束后丢弃写盘 |

实现要点：
- RSI 反思 run 使用 `origin='rsi_reflect'`，`args_new` 新会话，**禁止 `--resume`**；
  结束即销毁 `__rsi_reflect__` 槽，下一轮从零开始（避免跨 cycle 自我强化）。
- 评估 L1 用 `utility.generate` 的临时目录，不创建角色会话；L2 用 shadow home，
  从版本快照构建，不挂载真实 `data/agents/<slug>`；`ANVIL_ENDPOINT`/`ANVIL_TOKEN`
  清空，`ANVIL_EVAL_MODE=1`。
- 投影排除：任务 workspace 的 `CLAUDE.md`/context 不注入 `.anvil/rsi`、
  `.anvil/space-versions`、`data/eval`、`data/runtime-proposals`；角色运行时环境
  不含 `ANVIL_EVAL_KEY`（若启用隐藏集加密）。
- 信息流只允许：`任务证据 → RSI`（脱敏摘要）；`评估 → RSI`（只给聚合 diagnosis，
  不给 item/单例结果）；`RSI → 评估`（只给候选 manifest/Strategy 快照，不给反思
  transcript）；`人工 UI` 是唯一能看到全部的地方。
- 测试：`test_rsi_context_isolation.py`（无 resume、无任务 transcript、无隐藏集明文）、
  `test_eval_context_isolation.py`（shadow home、无真实 home 写、无 endpoint/token、
  真实 home 前后 hash 一致）。

## 2. 组件 1：角色 RSI 自迭代算法

### 2.0 形式化目标

设角色在时刻 t 的空间状态为 `R_t = (Charter_t, Strategy_t, Experience_t)`，Charter 在
一个演化周期内固定（只读）。每批观测 `E_t` 后，评估输出方向 `D_t`（§3.8）。
反思器 `Π` 生成候选集合：

```
C_t = Π(R_t, E_t, D_t, OperatorStats_t, NegativeResults_t)
C_t = { R_t ⊕ δ_j | δ_j 是 §2.5 允许的有界编辑，≤2 edits/candidate }
```

评估器 `Q(c; suite)` 返回分维度向量与 verdict。选择：

```
v* = argmax_{c ∈ C_t ∪ Archive_t} U(c)
     s.t. charter_guard(c)=1, safety(c)=0,
          held_in Δ ≥ 0, held_out Δ ≥ 0,
          CI_low(Δ) > noise_floor 或人工 waiver,
          cost(c) ≤ 1.5 × cost(active),
          n_pairs ≥ N_min
Archive_{t+1} = Archive_t ∪ C_t ∪ {verdicts, negative results}
R_{t+1} = promote(v*)  （仅人工批准；v1.50 不自动晋级）
```

其中 `U` 见 §3.2；`Archive` 是 `proposals` + `role_versions` + `eval_runs` 的并集。
`R_t ⊕ δ` 只允许改 Strategy/Experience，不允许改 Charter/runtime（§1.1）。
这个形式化的关键是：**方向 `D_t` 是输入，候选是文本 delta，选择是带硬约束的多目标
优化，硬约束（Charter/安全/非劣/成本/样本量）优先于分数**。

### 2.1 触发策略（每任务回执，按批次反思）

| 触发 | 条件 | 动作 |
|---|---|---|
| 量 | 自上次 cycle 以来该角色 ≥3 条新 observation | 入队反思 |
| 严重度 | 一次人工最终驳回，或失败签名簇计数 ≥2 | 入队反思（优先） |
| 周期 | 每角色每周一次 | 入队反思 |
| 冷却 | 距上次反思 <24h | 跳过 |
| 上限 | >1 次/天 或 >3 次/周/角色 | 跳过并记录 |
| 预算 | RSI 日 token 预算或全局预算耗尽 | 跳过并记录 |
| 评估 | 候选会改总是注入的 Strategy/playbook | 入队评估（若开关开启） |
| 巩固 | 5 个已应用候选或 30 天 | 入队巩固候选 |
| 运行时 | 失败 run 或每日扫描 | 运行确定性检测器 |

排除：纯 @ 回复 run、planner run、findings run、无角色步骤的任务、dispatch 子任务
（证据归并到父任务）。

成本控制：反思 run 输出 ≤30k tokens、10 分钟超时；每角色同时 1 个活跃反思；
每 cycle ≤2 条候选、每候选 ≤2 条编辑。

### 2.1.1 执行时机（推荐）

**原则：观测立即做；反思在“信号齐、角色闲、预算够”的窗口做；评估在离线窗口做；
晋级只在人审时做。**

| 动作 | 最佳时机 | 说明 |
|---|---|---|
| observation / harvest_seed | 任务 done / 最终驳回 / step 失败 / 返工时**同步** | 零 LLM、幂等；证据最新；不阻塞任务 |
| 反思（普通） | 满足触发后，角色空闲 + 系统低负载 + 预算可用的**下一个 tick**；优先夜间窗口 | 批量 ≥3 observations；不抢占任务 |
| 反思（严重） | 驳回/失败簇≥2 时**下一个空闲窗口尽快**（可当天） | 优先级最高，但不打断正在跑的任务 |
| 反思（暂缓） | 任务仍在 `in_review` 且预期人审未结束 | 人审 verdict 是最强信号；等 review 结束再反思，严重失败除外 |
| 候选评估 | **夜间/周末批处理**，EvalRunner 并发 1；系统空闲时 | 回放昂贵；避免与角色 daemon 抢资源 |
| 人工晋级 | 每日 Inbox 摘要 / 人工有空时 | 不自动；批量审阅 |
| SOAKING 监控 | 晋级后持续滚动窗口 | 不额外调用模型，只聚合指标 |
| 巩固 | 每周/每月低峰 | 低优先级 |
| 运行时检测 | 每日低峰扫描 | 确定性，便宜 |

**静默窗口判定**（全部满足才跑反思）：
1. 角色无活跃 task run；
2. 全局活跃 run 数 < `rsi.max_global_active_runs`（默认 1–2）；
3. 当前时间在 `rsi.quiet_hours`（默认 22:00–06:00）或人工手动触发；
4. RSI 预算可用；
5. 该角色没有“同一任务仍在 in_review”的待定证据（严重失败/驳回除外）；
6. 角色没有待领取/待派发的任务（有则先服务任务）。
不满足 → 写 `rsi.deferred`（带原因），下个 tick 重试；超过 TTL（默认 24h）升级为
人工提醒，避免永远饿死。**反思 run 可被任务唤醒抢占**（§2.3.1），任务永远优先。

**为什么不在每个任务完成时立刻跑 LLM**：
- 单任务样本=1，无法判断改进/退化；
- 任务刚结束，角色上下文仍带执行惯性，反思容易“自我合理化”；
- 人审 verdict 未出，可能把“会被驳回”的失败当成功；
- token 成本随任务线性增长，且会与下一个任务抢角色进程；
- 批量后可以用多条任务做失败签名聚类，提案质量更高、噪声更低。

**为什么不只每周跑一次**：
- 严重失败/驳回是时间敏感信号，等到周末会积累重复错误；严重度触发可当天在空闲窗口跑；
- 普通任务仍按 ≥3 条 observation 或每周，避免碎片化反思。

**调度映射**：
- `evolution` tick 建议 60s；只做 due 检查、入队、reap，不调模型；
- 反思由角色 daemon 执行，受静默窗口约束；
- EvalRunner 独立线程，默认只在 `rsi.eval_window`（默认 01:00–05:00）启动；
- 所有 deferral/skip 写 events，UI 可见（不静默丢弃）。

证据包（脱敏、≤12k 字符、不可信内容分隔）：

```json
  "portrait": {"digest":"sha256:...","responsibilities":["..."],"capabilities":{"...":0.8}},
  "strategy": {"version":7,"instruction_sha":"...","principles_sha":"...","playbook_ids":["N-..."]},
  "episodes": [
    {"task_id":"T-...","step_id":"S2","status":"approved","rework_count":0,
     "failure_class":null,"gate":"human_review","cost_tokens":1234,
     "summary":"...","evidence_refs":["event:..."]}

  "clusters": [
    {"signature":"sha1:...","cause":"acceptance_command_not_run",
     "behavior":"submitted_without_verification","mechanism":"verification_discipline",
     "count":3,"episode_refs":["T-...:S2"]}
  ],
  "online_metrics": {"first_pass_rate":0.62,"rework_rate":0.21,"human_reject_rate":0.08},
  "diagnosis": {"...":"最近一次评估的方向向量，仅聚合值"},
  "operator_stats": [{"operator":"append_playbook_item","attempts":5,"promotes":2,"regressions":0}],
  "negative_results": [{"candidate_id":"P-...","reason":"regressed cost","signature":"..."}]

```

失败签名 `φ = (cause, behavior, mechanism)`，确定性聚类（精确三元组哈希，不做 embedding）：

| 分量 | 来源 | 归一化枚举 |
|---|---|---|
| `cause` | gate/decision 驳回原因、step `failure_reason`、人工反馈类别 | `acceptance_missed`、`wrong_file_scope`、`missing_verification`、`bad_handoff`、`tool_unavailable`、`unclear_plan`、`other` |
| `behavior` | step/run/activity/evidence 模式 | `submitted_without_verification`、`ignored_retrieved_knowledge`、`overlong_summary`、`scope_drift`、`repeated_command_failure`、`no_evidence`、`other` |
| `mechanism` | 可复用干预目标 | `verification_discipline`、`context_retrieval`、`scope_alignment`、`decomposition_quality`、`handoff_quality`、`tool_selection`、`cost_efficiency`、`knowledge_authoring`、`safety_compliance` |

簇可入选：≥2 个 episode，或一次高严重度人工驳回。摘录脱敏（密钥/token/绝对 home 路径），
一律标注为数据、不得执行。

**知识领域过滤**：以 Charter 的 `responsibilities`/`capabilities` + 任务 `tags/repo` 判定
范围。角色私有经验卡可写；topic/channel 卡仅限任务已绑定且去重后补充，写 `proposed`；
越界知识只能降级为共享经验提案（人工批准），不得写入角色空间。Cindy 仍负责任务级/
主题/频道整体收割；角色负责“本角色视角”的经验与领域洞察，二者按
`source_task + title + body hash` 去重。

### 2.3 反思 worker（角色 run，独立上下文）

- 新增 run：`runs.create_run(..., origin='rsi_reflect', task_id=None)`，prompt 前缀
  `[anvil:rsi-reflect]`；独立上下文槽 `__rsi_reflect__`（`daemon_common.context_key` /
  `context_engine` 对 `origin='rsi_reflect'` 返回该 key），不与任务 slot 共用；
  **每 cycle 新会话（`args_new`，禁止 `--resume`），完成即销毁槽**，不携带上一轮
  反思上下文（§1.6）；
- 落点：`graph/nodes.py:499-523` `_run_prompt_kind()` 增加 `rsi_reflect` 分支（在
  `findings` 之后、`step` 之前）；`graph/nodes.py:526-540` `_protocols_for_run()` 返回
  新增的 `render.RSI_REFLECT_PROTOCOL`；`tests/test_prompt_snapshot.py` 锁定分类；
- 使用角色自己的 runtime 和身份（满足“角色自己迭代”），但不进入任务会话；
  走现有 run 日志与 `token_usage` 记账；`_prompt_for_run` 使用 RSI 协议，避免
  claim/submit 协议；
- 只读：无工具或仅只读 `anvil rsi` 查询；不允许写运行时/网络；输出走最终 JSON；
- 可选 critic pass：同一 run 第二个 JSON 对象，或高风险候选另起一次 run，专门尝试
  证伪候选；critic 失败不阻塞；
- 解析：从 run log `[result]` 提取 JSON；schema 校验失败重试一次（仅格式纠正）；
  再失败标记 `reflection_failed`，不影响任务；
- 评估 judge 不走角色 run：用 `services/utility.generate()`（固定 judge prompt/运行时，
  不污染角色会话）并记录 runtime/model 版本；judge 优先选**与角色不同的**默认运行时/
  模型，降低同源偏好；L2 任务回放才需要 shadow 执行环境。

### 2.3.1 RSI 运行时角色处于什么状态

RSI 反思是**角色的 no-task run**，不是任务执行：

- run 形态：`origin='rsi_reflect'`、`task_id=None`、无 step/workflow/lease/claim；
  不进入任务时间线，不写 `task_role_claims`，不持有租约；
- 角色状态：现有 `services/role_state.derive_task_role_state` 仍按任务派生；UI 额外显示
  **`evolving` 徽标**（存在活跃 `rsi_reflect` run 时）。它不算“工作中”，但调度器把它
  当作**短暂忙**：RSI 运行期间不向该角色派新 step（通常 ≤10 分钟），不抢占已在跑的
  任务；角色在跑任务时 RSI 一律 defer（§2.1.1 静默窗口）；
- **任务优先 / 可抢占**：若角色在 RSI 期间收到任务/step 唤醒，立即 `rsi.preempt(role)`：
  终止反思 run、销毁 `__rsi_reflect__` 槽、写 `rsi.preempted`，先服务任务；被打断的
  cycle 下个静默窗口重跑。**任务调度永不等待 RSI 超过一次工具边界**；RSI 是低优先级
  后台工作，不能成为任务延迟的原因；
- 会话：独立 `__rsi_reflect__` 槽，新会话（`args_new`，不 resume），任务会话/任务
  context slot 完全不受影响；run 结束销毁该槽，角色回到 idle；进程是否保留由现有
  idle release 决定；
- 读写：反思进程只读 Charter/Strategy/证据包/聚合 diagnosis；**不写角色文件**。
  知识卡、候选、RIP 都由后端在 run 结束后校验并写入；因此 RSI 运行时角色空间不会被
  半成品污染；
- 计数：token 计入 `token_usage`（origin=`rsi_reflect`），受角色并发/预算约束；
  不阻塞人工评审，不影响任务 `in_review`；
- 评估阶段：L1 judge 不涉及该角色；L2 用 shadow 副本，**活角色完全不参与**；
- 晋级阶段：人工批准后写角色文件；若角色正在跑任务，新 Strategy 从下一次 run 生效，
  当前 run 继续用 frozen snapshot。

状态流转：

```
idle ──(due & quiet window)──► evolving ──(run done)──► idle
working ──(due)──► deferred(working) ──(task done & idle)──► evolving
```

测试：`test_rsi_role_state.py` 断言 `evolving` 派生、任务 claim/lease 不受影响、
RSI 期间新 step 延后、run 结束槽销毁。

### 2.5 候选编辑算子与边界

| 算子 | 档 | 目标 | 限制 |
|---|---|---|---|
| `K1 append_knowledge_card` | 自主 | 角色私有经验卡 | 每 cycle ≤2（且每来源任务 ≤2）；质量门 + 实践门；去重哈希 |
| `K2 revise_knowledge_card` | 自主 | 角色私有经验卡 | 一次一张；保留证据 |
| `K3 link_or_confidence_update` | 自主 | 角色知识元数据 | 不产生新主张 |
| `P1 append_playbook_item` | 人工审批 | `notes/playbooks/<name>.md` | 每 cycle ≤1；≤400 字符 |
| `P2 revise_playbook_item` | 人工审批 | playbook 条目 | 一条；diff ≤400 字符 |
| `P3 prune_playbook_item` | 人工审批 | playbook 条目 | ≤20% |
| `S1 append_principle` | 人工审批 | `PRINCIPLES.md` | 每 cycle ≤1 行；总量 ≤2048 字符 |
| `S2 replace_strategy_block` | 人工审批 | `instruction.md` Strategy 段 | 段内 ≤400 字符 delta；段 ≤4096 字符 |
| `C1 propose_charter_change` | 只提案 | 现有 `proposals`（kind=`portrait`） | 字段 allowlist；不直接应用 |
| `R1 propose_runtime_component` | 只提案 | `runtime_proposals`（RIP） | 只能证据，不应用 |
| `N no_change` | — | 只写事件 | 必须给理由 |

全局限制：
- 每 cycle ≤2 条候选，每候选 ≤2 条编辑；每条 ≤400 字符；不得整段重写；
- 不得新增依赖、不得写工具调用脚本、不得删除安全/边界条目；
- 不得改 Charter 标记、`description`、`runtime`、`permissions`、工具/技能绑定；
- 每条必须带 `portrait_refs`、`diagnosis_ref`、证据引用、预测效果与回归风险
  （AHE 的“可证伪编辑”）；无诊断引用默认拒绝；
- 静态 lint：禁词（忽略审批/绕过评审/改运行时/关闭测试）、密钥模式、超长、编码异常、
  路径穿越、跨角色 note 导入。

### 2.6 候选归档与状态机（复用 `proposals` + `events`）

候选归档复用现有 `proposals` 表；**不新建 cycle 表**。`proposals` 扩展：
`kind`（`portrait|strategy|experience`）、`tier`、`cycle_id`、`base_version`、
`applied_version`、`parent_id`、`dedupe_key`、`evidence_json`、`manifest_json`、
`predictions_json`、`diagnosis_json`、`eval_id`、`updated_at`、`decided_by`、
`decision_note`。现有 `anvil self propose` 行保持 `kind='portrait'`、
`tier='proposal_only'`、`status='pending'`，向后兼容。

状态机（状态存 `proposals.status`，迁移写 `events`）：

| 状态 | 进入 | 出口/守卫 |
|---|---|---|
| `OBSERVING` | 任意 | 有足够证据的 `rsi.observation` |
| `ELIGIBLE` | 触发条件满足 | 预算可用 → `QUEUED` |
| `QUEUED` | 反思 run 已入队 | run 创建 → `REFLECTING` |
| `REFLECTING` | `origin='rsi_reflect'` run 活跃 | 有效候选 → `CANDIDATE_READY`；无变化 → `NO_CHANGE`；无效 → `REJECTED` |
| `CANDIDATE_READY` | schema/guard 通过 | 自主 → `APPLYING`；审批 → `PENDING_HUMAN`；需评估 → `EVALUATING` |
| `EVALUATING` | eval run 活跃 | promote/inconclusive/reject |
| `PENDING_HUMAN` | 等待人工 | 批准 → `APPLYING`；拒绝 → `REJECTED` |
| `APPLYING` | CAS 成功 | 写版本 → `SOAKING` |
| `SOAKING` | 在线观察窗（默认 5 episodes/14 天） | 稳定 → `STABLE`；退化 → `ROLLING_BACK` |
| `ROLLING_BACK` | 自动或人工 | 恢复上一版本 → `ROLLED_BACK` |
| `NO_CHANGE` | 角色输出 no_change | 归档事件，回到 `OBSERVING` |

**概念状态 vs 落库状态**：上表的 `OBSERVING/ELIGIBLE/REFLECTING/SOAKING/STABLE` 是从
`events` 派生的外层状态，不写入 `proposals.status`；`proposals.status` 只用
`draft`（CANDIDATE_READY）、`queued`（REFLECTING 入队）、`evaluating`、`pending`
（PENDING_HUMAN）、`applied`（APPLYING/SOAKING/STABLE）、`rejected`、`inconclusive`、
`superseded`、`rolled_back`、`no_change`。这样既有完整审计，又不在两张表里重复状态。

守卫：每角色+目标同时 1 个活跃候选；1 个应用在途；≤2 编辑；charter_digest 一致；
无禁止目标；预算未耗尽；审批档必须人工；重复 dedupe_key 拒绝。

Pareto 归档：
- 每个已尝试的 strategy 版本是点 `(quality, cost_per_success)`；archive 保留
  source/scores/evidence/lineage；
- `v1 ≻ v2` 当且仅当 `success1≥success2`、`quality1≥quality2`、`cost1≤cost2` 且至少
  一项严格；被支配候选不能直接晋级，除非人工 waiver 并记录；
- 新候选父代从 Pareto set + 当前版本采样，不只沿最新 lineage；
- 负结果（rejected/regression/failed prediction）永久保留，反思 prompt 引用。

### 2.7 评估、晋级、应用、回滚

- 评估触发：候选改 Strategy/playbook（总是注入）→ 若 `role_rsi_evaluation` 开启则评估；
  经验卡（检索型）不评估，直接应用。
- 评估结果三态：
  - `promote` → `PENDING_HUMAN`（Inbox 立项）；
  - `reject` → `REJECTED`，负结果归档；
  - `inconclusive` → 保持候选，继续积累；人工可写理由 override，默认不晋级。
- 人工晋级：
  - 仅 `require_human`；展示 diff、证据簇、预测、评估报告（CI/样本量/噪声/judge 版本）、
    回归风险；
  - 批准 → `RoleSpace.apply()` 原子应用；拒绝 → 记录理由，归档。
- 应用：
  1. 校验 charter_digest 与 base 一致；
  2. 原子写回 `instruction.md`/`PRINCIPLES.md`/`notes/memory/cards/**`/`notes/playbooks/**`
     （临时文件 + rename）；
  3. 写 `role_versions(kind='evolution', status='active')`，旧 active 置 archived；
  4. 审计 `rsi.candidate_applied` + SSE；
  5. 可选 git commit（仅当 `agents/.git` 存在）。
- SOAKING / 回滚：
  - 晋级后进入观察窗；在线滚动指标（20 episodes）连续 2 个窗口退化超过噪声门槛 →
    自动回滚到上一已批准版本（只回到曾人工批准的状态），并通知；
  - 人工可随时回滚；回滚写入新版本 `source='rollback:<v>'`，不删历史；
  - 回归必须区分任务组合变化（分层对比 repo/workflow weight/gate/runtime/model）。
- 巩固（5 个已应用候选或 30 天）：
  - 去重经验卡/playbook，合并重叠条目，淘汰 90 天零命中且低于质量阈的卡；
  - 上限：PRINCIPLES 2048 字符、Strategy 段 4096 字符、playbooks 40 条/20KB、
    角色 notes 200 条 active；
  - 巩固本身也走候选 + 人工审批（经验卡自主）。

### 2.8 元学习（算子层面，P3）

- 算子固定为代码常量（`services/rsi_operators.py`），角色不能新增算子；
- 从候选归档统计每个算子的 attempts/promotes/rejects/regressions/mean delta；
- 用 Laplace 平滑分数 + UCB 探索项排序；近 20 次中某算子占比 >60% 时降权，防止
  多样性坍塌；
- 连续被拒的算子，反思 prompt 注入负结果摘要并降低优先级；
- 预测准确性：候选记录 `predicted_effect`；SOAKING/下一轮评估比较实际 Δ，
  `prediction_accuracy = 1 - |predicted-observed| / max(|observed|, δ_min)`（按指标归一化，
  裁剪 [0,1]）；写入评估报告与反思 prompt；
- v1.50 不自动晋级（`role_rsi_auto_promote=false`），算子元学习只影响提案排序。

### 2.9 RSI 主循环伪代码

```text
on_task_done(task):
    for role in participants(task):
        emit_once("rsi.observation", key=sha1(role|task|completion_key), evidence=digest(task, role))
        if due(role, observations): enqueue_reflection(role)

tick():
    for role in due_roles(budget, priority):
        run = create_run(role, origin="rsi_reflect")
        out = parse(run.result)                    # 严格 JSON
        ingest_knowledge(out.knowledge_items)       # autonomous/proposed + quality gate
        ingest_role_proposals(out.role_proposals)   # proposals kind=portrait
        ingest_runtime_issues(out.runtime_issues)   # runtime_proposals
        for edit in out.edits:
            validate(edit, charter_digest, portrait_refs, limits)
            if edit.tier == "autonomous": apply_knowledge(edit)
            else: create_proposal(kind="strategy", manifest=edit)
    for cand in due_candidates():
        if touches_strategy(cand) and eval_enabled:
            result = evaluate(cand, suite)          # §3
            transition(cand, result)
        else:
            transition(cand, "PENDING_HUMAN")
    soak_and_rollback()
```

**算法逻辑逐段解释**

输入：任务完成/失败/返工/驳回信号、active Strategy、最近一次 `EvaluationReport`、
算子统计、负结果归档。输出：知识卡、角色提案、RIP、候选编辑（proposals）、版本晋级。

1. **`on_task_done`（确定性、零 LLM）**
   - `participants(task)` 取 assignees/assignee/step role/claims/planner，排除系统身份；
   - 对每个角色从现有表拼证据摘要，写一条幂等 observation（key 含 `completion_key`，
     重试不重复、reopen 后再次完成会产生新 observation）；
   - `due()` 只判断“是否够条件入队”，不在任务完成路径跑模型；失败被 try/except 隔离，
     不阻塞 `done`，由 scheduler backfill 补漏。
   - 目的：满足“每个任务完成都有收割回执”，同时把成本从 O(任务数) 的 LLM 调用
     降为 O(批量) 的反思调用。

2. **`tick` 选角色**
   - `due_roles` 按严重度（失败/驳回优先）→ 新 observation 数 → 等待时长排序；
   - 同时检查冷却（24h）、每日/每周配额、全局/角色 token 预算、每角色单活跃 run；
   - 跳过不是失败：写 `rsi.budget_skipped`，下个 tick 继续。

3. **反思 run**
   - 使用角色自己的 runtime 与身份，但独立上下文槽，不污染任务会话；
   - prompt 注入 Charter digest、active Strategy、证据包、最近 diagnosis、算子目录/
     统计、负结果；要求严格 JSON；
   - 解析失败重试一次（只做格式纠正）；再失败记 `reflection_failed`，不升格为候选。

4. **四类产出分流**
   - `knowledge_items`：角色私有卡走自主档（实践门+质量门+去重）；topic/channel 卡只写
     proposed；shared 只生成 lesson pending；
   - `role_proposals`：只允许 responsibilities/capabilities/tools/skills/MCP，写现有
     `proposals(kind=portrait)`，人工审批；runtime/model 不在此列；
   - `runtime_issues`：分类、去重、生成 RIP draft；角色不写运行时；
   - `edits`：先做静态校验（target/tier/limits/charter_digest/portrait_refs/
     diagnosis_ref/禁词），自主档直接应用，审批档生成 strategy candidate（proposals）。

5. **候选批次与评估**
   - pending edits 按角色/base version 聚合；同一角色同时最多一个 candidate；
   - 改 Strategy/playbook（总是注入）才需要评估；经验卡不评估；
   - `evaluate` 返回三态；`promote` 进入人工 Inbox，`reject` 归档负结果，
     `inconclusive` 保留候选继续积累；任何状态迁移走 CAS。

6. **应用与 SOAKING**
   - 人工批准后原子写文件 + 写 strategy 版本；旧 active 归档；
   - 观察窗内在线指标连续 2 个窗口退化超过 noise floor → 自动回滚到上一个已批准版本；
   - 人工可随时回滚；回滚也是新版本，不删历史。

**关键不变量**：observation 幂等；候选 dedupe + 单活跃；charter_digest CAS；
审批档必须人工；评估器不读角色空间；RIP 不自动应用。**复杂度**：每任务 O(参与者数)
确定性写入；每角色每次反思 1 次模型调用；评估 O(2×items) 次回放 + O(B×n) bootstrap。

## 3. 组件 2：迭代效果评估算法

评估输出不是“一个分”，而是 **fitness vector + diagnosis/direction**，直接作为 RSI 的
输入。核心原则：评估器在演化循环之外、只读、角色不可见；确定性 verifier 优先；
证据不足输出 `inconclusive`，绝不为了“有结论”而晋级。

### 3.1 角色 episode 与归因

- **episode** = `(task, step)`，其中 `workflow_steps.role_slug = role`；无 workflow 的
  任务只有在**单一 assignee** 时才作为 episode；多角色任务级结果不用于归因。
- 只归因给拥有该 step 的角色；不把下游成功归给上游角色。
- 排除 `closed`、skipped、基础设施失败（`platform_timeout/spawn_error/lease_expired/
  environment`）出能力分母，单独报告。
- 在线样本：指标 ≥5 episodes，滚动趋势 ≥20；不足 → `inconclusive`。
- 版本错位：按 `run.profile_snapshot` / 任务创建时的 strategy version 分组；不同版本
  在线信号不混算；候选版本的证据只来自回放/评估，不把晋级后任务算到候选头上。
- 多角色贡献不可完全分离；v1.50 用 step 级归因，报告中标注局限。

### 3.2 指标定义

| 指标 | 定义 |
|---|---|
| `success` | step `approved` 且 task `done`；非 workflow 时 task `done` |
| `first_pass` | success 且 `rework_count=0` 且无 reject decision |
| `rework_rate` | `sum(rework_count>0)/n` |
| `human_reject_rate` | 角色 step 上 reject decisions / 全部 decisions |
| `failure_rate` | 非基础设施失败 step / n |
| `cost_per_success` | 角色 episode 的 input+output+cache tokens / max(1, successes) |
| `p95_latency` | step wall-clock P95 |
| `knowledge_reuse` | `context_manifests` 中包含角色/知识块的 episode / n |
| `knowledge_effect` | `knowledge_feedback` applied/helpful vs unhelpful/no_effect；不用 LLM judge |
| `safety_compliance` | 1 − 越权/Charter 违规 episode / n |
| replay `pass@1` | 全部 hard verifier checks 通过 |
| replay `score` | 加权 checks 通过比例 [0,1] |

复合效用（仅排序/门控，不替代分维度展示）：

```
U = 0.45 * success_rate
  + 0.30 * (quality / 100)            # quality 来自 replay/rubric
  + 0.15 * efficiency_score           # min(1, baseline_cost / cost)
  + 0.10 * knowledge_utility          # 0.4*adoption + 0.4*use + 0.2*feedback
```

候选的 `success_rate` 无 L2 时用 L1 `predicted_success` 代理，报告中必须标注来源；
`cost` 无 L2 时用策略文本增量代理；不得把代理值写成“真实成功提升”。

### 3.3 隐藏回放集（真实任务，隔离存储）

- **来源**：已完成且 `done` 的真实任务，至少一个 approved step + 可复用 verifier
  （验收命令/测试/产物检查）；**只允许人工策展**：
  `anvil rsi suite add --task <id> --step <id> --split held_in|held_out --file item.json`；
  角色不能读/写 suite；不生成合成任务、不改写 prompt、不做变体。
- **隔离（必做，主防线）**：`data/eval` 独立目录 0700，只允许 human/evaluator 访问；
  不进入角色投影/上下文/CLI/日志；diagnosis 不含 item ID；回放前后哈希真实 role home；
  evaluator 代码/suite manifest 每次运行前哈希校验。
- **加密（可选，默认关闭）**：`rsi.eval.encrypt_hidden=0`。开启时 item 用 AES-GCM
  落盘，key `ANVIL_EVAL_KEY` 只在 evaluator 进程，加入 `util._AGENT_SECRET_ENV_KEYS`，
  每次解密写审计。
  - **为什么加密**：主要不是防恶意 shell（单机同 OS 用户下，agent 仍可能读进程/文件，
    加密不是硬边界），而是防止隐藏集明文泄漏进备份、DB、日志、UI、上下文，并让
    “照着评测集过拟合”从顺手变成刻意行为；同时提供解密审计。
  - **不加密时的依赖**：上面的目录隔离 + ACL + 不暴露路径/ID + 人工审计。若机器共享、
    备份不可信或需要更强审计，再开启加密。
- **item schema**（文件；可选加密）：

```json
{
  "schema_version": 1,
  "item_id": "R-...",
  "suite_id": "role-rsi-default",
  "split": "held_in",
  "family": "repo:openssl;mechanism:verification",
  "source": {"task_id":"T-...","workflow_id":"W-...","step_id":"S2","role_slug":"backend-dev"},
  "prompt": {"task_title":"...","task_description":"...","step_instructions":"...","acceptance":["..."]},
  "workspace": {"kind":"git_snapshot","repo":"openssl","commit":"...","setup":["..."],"digest":"..."},
  "verifier": {
    "kind":"deterministic",
    "checks":[{"id":"c1","cmd":"...","expect_exit":0,"weight":1,"hard":true}],
    "forbidden_changes":["tests/**",".anvil/**"],
    "timeout_seconds":900,
    "token_cap":60000
  },
  "rubric": null,
  "provenance": {"original_outcome":"approved","evidence_digest":"..."}
}
```

- **split**：
  - `held_in`：用于诊断/方向；RSI 只看簇签名与脱敏摘录，不看原始 item/期望答案；
  - `held_out`：只用于验收；RSI 永不见 item 内容/ID/单例结果，只看聚合 Δ 与 CI；
  - family（repo + mechanism）在 held-in/held-out 间**不相交**，衡量迁移；
  - 最低 8+8 才授予晋级权限（建议 12+12）；不足 → `inconclusive`，只能人工 override；
  - suite 内容寻址版本化；任何 item 变更产生新 suite 版本，eval run pin digest。
- 目录：`data/eval/suites/<suite>/`、`data/eval/runs/<eval>/`、`data/eval/work/`，权限 0700。

### 3.4 配对回放执行

- 双臂：baseline（上一已晋级 strategy 版本或候选前版本）与 candidate，同一 item；
- 同 runtime executable/version、同 model id、同 timeouts/token caps；顺序按
  `hash(eval_id, item_id)` 平衡，降低时间漂移；
- 重复：常规 `k=1`；canary 子集与 A/A 校准 `k=2`；预算不足则 verdict 封顶 `inconclusive`；
- 隔离：临时 shadow data dir + 临时 role home（从候选版本快照构建，不挂载真实
  `data/agents/<slug>`）；无 `ANVIL_ENDPOINT`/`ANVIL_TOKEN`；`ANVIL_EVAL_MODE=1`；
  对 shadow home 的写盘丢弃；回放前后哈希真实 role home，任何变化 → eval 失败；
  评估是独立上下文，不读角色任务会话/RSI 反思 transcript（§1.6）；
- 角色运行时能看到 item prompt（不可避免），但**看不到 verifier 命令/期望输出**；
  verifier 由 evaluator 执行，不由角色执行；
- verifier 规则：hard checks 必须全过才算 pass；forbidden changes（tests、Anvil 配置、
  evaluator 路径）立即失败；超时/token cap → `budget_exhausted` 失败；
- 成本：单 item ≤60k tokens，单 suite ≤1.5M，单角色默认 ≤1 次评估/周；超限 abort →
  `inconclusive` + 通知。

### 3.5 统计门控

对每个 split：

- `Δ_i = score_candidate(i) − score_baseline(i)`（配对）；
- `Δ = mean(Δ_i)`；按 family 分层的 bootstrap（默认 2,000 次；可配 10,000）取 95% CI；
- `noise_floor = max(0.02, q95(|Δ_AA|))`，来自周期性 A/A（baseline vs baseline）；
  无 A/A 数据时用 0.10，且 suite <12 时 verdict 封顶 `inconclusive`；
- `minimum_effect = 0.05`（可按 suite 配置）。
- 在线信号用于监控、漂移告警与诊断方向，**不作为晋级判定**（任务组合/人员/模型漂移
  是混杂因素）；晋级只看隐藏回放的配对结果。

| Verdict | 条件 |
|---|---|
| `promote` | held-in Δ ≥ 0 且 held-out Δ ≥ 0；至少一个 split 点估计 ≥ minimum_effect 且 CI 下界 > noise_floor；无 hard 约束/安全回归；cost ≤1.5× baseline |
| `reject` | 任一 split CI 上界 < −noise_floor，或 hard/safety 违规，或 forbidden changes |
| `inconclusive` | 其他（n 不足、无 A/A、CI 跨零、suite 低于下限） |

补充：
- 先检查 direction focus：`must_not_regress` 任一维度显著负向 → `reject`；
  `must_improve` 未达 minimum_effect → `inconclusive`；
- 只有预注册的主维度计入晋级；其他维度探索性，超过 3 个用 Holm 校正；
- `inconclusive` 永不自动应用；人工可用书面理由 override 并写入候选/审计；
- 多重比较与环境漂移（Anvil/runtime/model/OS/suite digest）在报告中显式记录。

### 3.6 Judge 校准（确定性优先）

- **主评估器是确定性 verifier**（命令、产物检查、forbidden diff）；
- rubric/LLM judge 在 v1.50 默认关闭（`ROLE_RSI_RUBRIC_JUDGE=0`）；开启时：
  - judge prompt 冻结在 evaluator 代码；judge runtime/model pin 在
    `eval_runs.integrity_json`；优先使用与角色不同的运行时/模型；
  - 固定人工标注集 ≥30 条真实产出校准，要求每维度 κ≥0.6；否则 judge 仅作参考；
  - 每 cycle 人工抽检 10% 判分；分歧强制 `inconclusive`；
- 知识卡质量不使用 LLM judge：沿用现有确定性质量门 + 在线效果统计。

### 3.7 漂移与完整性监控

- **环境漂移**：每次 eval 前校验 Anvil 版本、runtime executable/version、model id、OS、
  suite digest；任何变化需重新基线，跨版本比较无效；
- **A/A canary**：每 cycle 跑 4 个 baseline-vs-baseline item；baseline 分数漂移超过
  noise floor → `eval.drift`，暂停晋级；
- **在线漂移**：每角色滚动 20 episodes，与前窗口 bootstrap 比较；连续 2 次退化超过
  noise floor → 暂停 RSI 晋级并通知；SOAKING 内超阈值触发自动回滚；
- **数据漂移**：回放集冻结；在线任务组合变化只报告，不改变晋级决策；
- **评估器完整性**：每次 run 前哈希 evaluator 代码 + suite manifest；不一致阻止 eval；
- 所有 eval 记录 `integrity_json`（suite_digest/runtime/model/anvil_version/AA_noise/judge）。

### 3.8 方向策略（human 指定）与输出 schema

评估上下文除版本外还必须记录工作集：`policy.baseline_working_set_hash` /
`candidate_working_set_hash`。同一版本下工作集变化时，在线窗口不能直接混算；
晋级评估默认用**同一工作集**对照隔离编辑效应，工作集自身效果单独评估。

**方向策略**（human-only，存 `settings['rsi.focus.<role>']` 或 `definition.rsi.focus`）：

```json
{
  "weights": {"success":0.45,"quality":0.30,"efficiency":0.15,"knowledge":0.10},
  "must_improve": ["quality.evidence"],
  "must_not_regress": ["cost_efficiency"],
  "notes": "优先补验收证据，不要靠增加篇幅换分"
}
```

- `weights` 用于 §3.2 的 `U` 与 diagnosis 排序；默认值即上面的 0.45/0.30/0.15/0.10；
- `must_improve` / `must_not_regress` 进入评估门控：未满足则 `reject` 或 `inconclusive`；
- 反思 prompt 必须带上 focus；候选编辑与 focus 冲突直接拒绝；
- human 可在角色演化页调整 focus，变更写审计；RSI 不能改 focus（属于 Charter 配置）。

```json
  ],
  "integrity": {"suite_digest":"...","runtime_id":"claude-code","runtime_version":"...",
                "model_id":"...","anvil_version":"1.50.0","aa_noise_floor":0.03,"judge":null},
  "recommended_actions": [
    {"operator":"P1 append_playbook_item","target_dimension":"verification_discipline","priority":1}
  ]
}
```

`diagnosis` 的生成规则（不让 judge 自由发挥）：
- `clusters`：确定性 `(cause, behavior, mechanism)` 聚类；
- `dimensions`：`delta`/CI 来自回放；`status` 由门槛规则给出；
- `suggested_operators`/`recommended_actions`：固定“维度 → 算子”映射表；
- `regressions`：hard 约束回归 + 成本回归；
- held-out 的单例数据永不进入 diagnosis。

RSI 反思 prompt 必须引用 diagnosis；候选与 `regressions`/禁止方向冲突直接拒绝；
下一轮评估检查 `falsifiable_check` 是否兑现，并更新算子统计。

### 3.9 防作弊 / 评估完整性

- 评估器代码、judge prompt、隐藏集、verifier 均不在角色可编辑面；角色 token 无写权限；
- 隐藏集隔离（独立目录 + ACL；可选加密）+ 不暴露路径/ID；反思 prompt 只给聚合 diagnosis；
- 静态检测：候选不得关闭测试、删除验收、伪造证据、提升 reasoning budget、改 evaluator；
- 人工抽检：每 cycle 10% judge 结果；每 N 次晋级抽 1 次人工复核；
- 过拟合监控：held-out 与 held-in 增益差距 > 阈值 → “疑似过拟合”，拒绝晋级；
- 预算/超时/环境 pin 见 §3.4/§3.7。

### 3.10 评估伪代码

```text
evaluate(role, candidate, suite):
    if not charter_guard(candidate): return reject("charter")
    if safety_violations(candidate): return reject("safety")
    check_integrity()                              # code/suite/runtime/model hash
    fit, hold = suite.held_in, suite.held_out
    if len(fit) < 8 or len(hold) < 8: return inconclusive("suite too small")
    l2 = paired_replay(candidate, active, fit + hold)   # deterministic verifier
    delta = stratified_bootstrap(l2, B=2000)            # by family
    noise = aa_noise_floor()
    if delta.ci_low <= max(minimum_effect, noise): return inconclusive
    if delta.tokens.ratio > 1.5: return reject("cost")
    if delta.held_in < 0 or delta.held_out < 0: return reject
    if not any(delta[k].ci_low > noise for k in ("U","success","quality")): return inconclusive
    return promote
```

无 L2（无可用 verifier）时：允许 L1 rubric judge（若开关开启、κ 达标）产出诊断，
但 verdict 封顶 `inconclusive`，只能人工 override 晋级。

**算法逻辑逐段解释**

输入：候选 manifest、active Strategy、隐藏 suite（held-in/held-out）、确定性 verifier。
输出：`promote | reject | inconclusive` + diagnosis/direction。

1. **前置硬门（不花回放成本）**：Charter guard / 安全违规 → 直接 reject；评估器 hash /
   suite digest / runtime/model 版本不一致 → `abort`（环境变了，不是候选变差）。
2. **样本量门**：held-in <8 或 held-out <8 → `inconclusive`；没有回放就没有晋级权。
   这是对“个人样本量不足”的直接约束。
3. **配对回放**：同一 item 跑 baseline 与 candidate 两臂，同 runtime/model/timeouts，
   顺序按 `hash(eval_id,item_id)` 平衡；逐项算 `Δ_i`。配对设计消除了任务难度、
   任务组合、人员等混杂因素。
4. **分层 bootstrap**：按 family（repo+mechanism）分层重采样，得到 `Δ` 的 95% CI；
   分层避免某个简单 family 主导结论。A/A（baseline vs baseline）给出 `noise_floor`；
   如果 `Δ` 不超过噪声，说明“看起来的提升”可能只是重跑波动。
5. **成本门**：candidate 成本 >1.5× baseline → reject；防止用更多 token 换分。
6. **非劣 + 改进**：held-in 与 held-out 的 Δ 都必须 ≥0（防回归）；至少一侧点估计
   ≥ minimum_effect（默认 0.05）且 CI 下界 > noise_floor（防噪声）、且无 hard 约束
   回归，才 `promote`；否则 `inconclusive` 或 `reject`。
   - held-in 负责“修目标”，held-out 负责“防过拟合”；family 不相交，衡量迁移。
7. **三态与人工 override**：`inconclusive` 永不自动晋级；人工可在书面理由下 override，
   写入候选/审计/评估报告。这样既不把噪声当结论，也不把系统卡死。

为什么顺序是“硬门 → 样本量 → 回放 → 噪声/成本 → 非劣/改进”：先排除不该评的候选和
不该花钱的环境，再花回放成本，最后用统计门槛避免把噪声或成本换来的分数当能力提升。
无 L2 时 L1 rubric judge 只产出诊断，verdict 封顶 `inconclusive`，因为“纸面判断”
不能替代真实执行结果。

## 4. 组件 3：运行时部件优化提案（RIP）

### 4.1 范围与分类

范围：运行时加载的、由 human 拥有的部件；不含角色 Charter/Strategy、Anvil 源码、
evaluator、隐藏回放集、安全策略（这些直接拒绝，走安全流程）。

| component_type | 覆盖 | 典型证据 |
|---|---|---|
| `skill` | `~/.claude/skills` 等 catalog 技能（SKILL.md/脚本） | 加载失败、触发不匹配、内容过时 |
| `mcp_server` | MCP 注册表/工具行为 | 连接失败、缺工具、鉴权、schema 不匹配 |
| `runtime_yaml` | `runtimes/*.yaml`（invocation/projection/catalog/capabilities） | 参数/投影/能力不匹配、版本越界 |
| `feature_flag` | 功能开关 | 行为与开关状态矛盾、任务类别需要新开关 |
| `tool_preset` | 工具预设/白名单 | 工具不允许、token 估算超限、闲置工具成本 |
| `model` | runtime/model | 上下文窗口、能力不匹配、路由失败 |
| `environment` | runtime 环境 | 可执行文件缺失/不健康、路径/OS、版本不匹配 |
| `harness_part` | 运行时投影/协议/模板 | 人工核实后归类 |
| `forbidden` | eval/security/anvil-source/role-config | 自动拒绝 |

判定规则：问题发生在角色可编辑面之外，且无法通过知识卡/策略/提案解决；必须附
“期望 vs 实际、命令、错误、复现条件、频率、临时绕过”。角色不得直接改运行时文件。

两个入口：
1. **即时入口**：角色在任务运行中遇到阻塞，可用 `anvil runtime propose` 直接提交
   （带当前 task/run/step 证据），不必等复盘；
2. **兜底入口**：反思从证据包抽取 `runtime_issues`，后端去重合并；另有确定性检测器
   每日扫描失败 run/步骤/配置不一致。
两个入口共用同一签名与生命周期，避免重复。

为什么角色不能直接改：运行时 skill/MCP/CLI/YAML 是**跨角色共享**的，一次改动会影响
所有角色；且这些目录不在角色 home 内。RIP 把“个案证据 → 可复现问题 → 建议修改 →
验收方式”整理成 human 可直接执行的文档，避免角色以局部经验污染全局运行时。

### 4.2 确定性检测器

`services/runtime_signals.py`（无 LLM）：

- 解析 `runs.log_path` 的已知错误模板（MCP handshake、missing tool、skill load、
  permission、command not found、context overflow）；
- 对比 `role_tools.skills/mcp` 与 runtime `catalog`；缺失条目/未选但必需的技能；
- 检查 `runtimes.status`、`last_probe_log`、executable path、version range；
- 检查失败 run/step 的 `failure_class ∈ {platform_timeout, spawn_error, context_overflow}`
  与重复 `agent_error` 模板；
- 扫描 gate/decision feedback 与 step `failure_reason` 的运行时关键词（不可信摘录）；
- 检测 feature flag/tool preset 矛盾。

检测器只创建 `draft` 提案与追加证据，不能把提案推进到 `open` 之后。

### 4.3 去重与生命周期

签名：
```
sig = sha256(component_type | component_key | runtime_id | runtime_version |
             normalized_error_class | normalized_message_template | phase)
```
归一化 ID/路径/数字/任务/run ID，保留 message template。活跃状态内一个 sig 一条提案
（partial unique index）；新证据追加 events 并增加计数，跨阈值升严重度。

阈值：7 天内 count≥2 或 critical → `draft`；count≥3 且跨≥2 task/role → 自动 `open`；
否则保持 draft 待人工/agent 复核。

状态机（human 独占流转）：
```
draft → open → triaged → accepted → implemented → verified → closed
                       └→ rejected | duplicate | wontfix | stale
```
- 角色只能 `create draft` 和 `append evidence`；
- `draft→open` 可由阈值或人工；`open` 之后全部人工；
- 实施完成后用提案里的“验收方式”做 probe；通过 `verified`，失败 reopen；
- 导出 md、应用运行时变更、关闭均由 human 执行。

### 5.4 调度器与评估 worker

- 保持 ≤12 域：新增 `evolution`（11 域），顺序锁定在 `maintenance` 之后；tick 建议 60s；
- `evolution` 阶段不调用模型，只查库、发事件、建 run/评估队列；
- **静默窗口**：`rsi_dispatch_reflections` 只在角色无活跃 run、全局活跃 run <
  `rsi.max_global_active_runs`、处于 `rsi.quiet_hours`（或人工触发）、预算可用时
  创建反思 run；否则写 `rsi.deferred`，下个 tick 重试，超 `rsi.defer_ttl_hours` 提醒人工；
- 任务仍 `in_review` 时暂缓以该任务为主要证据的普通反思（严重失败/驳回除外），
  等人审 verdict；
- `EvalRunner` 独立线程，lifespan 启动，`ROLE_RSI_EVALUATION_ENABLED=1` 且
  scheduler 开启时运行；**默认只在 `rsi.eval_window`（01:00–05:00）启动**；并发默认 1
  （最多 2），不与角色 daemon 抢资源；
- 预算：复用 `governance.daily_tokens_used`，新增 `rsi.daily_token_budget` 与
  `rsi.role_daily_token_budget`；耗尽跳过并记录；
- kill switch：`settings['rsi.enabled']='0'` 或功能开关停止新 cycle/eval；在途 run
  可被 reap 或允许完成但不晋级。

## 6. 安全、隐私、成本

- **HITL**：晋级/回滚/拒绝/运行时提案状态流转全部 `require_human`；agent token 403
  （复用 `deps.require_human`）。v1.50 固定 `role_rsi_auto_promote=false`。
- **评估器外部性**：evaluator 代码/judge prompt/隐藏集/verifier 与角色空间物理分离；
  每次 eval 前哈希 evaluator + suite manifest；角色不可见评估细节，只接收 diagnosis 聚合。
- **隐藏集隔离（主防线）**：独立目录 0700 + ACL + 不进入角色投影/上下文/日志 +
  diagnosis 不含 item ID；**加密是可选加固**（默认关闭）：开启时 AES-GCM +
  `ANVIL_EVAL_KEY` 仅在 evaluator 进程，agent 环境黑名单，每次解密审计。
  **本地信任声明**：单机同 OS 用户下，加密主要防误暴露（备份/DB/日志/UI/上下文）与
  非恶意过拟合，不是对拥有 shell 的恶意 agent 的硬隔离；最终控制是人工复核 +
  evaluator 哈希。
- **回放隔离**：shadow data dir/home、无 Anvil endpoint/token、`ANVIL_EVAL_MODE=1`、
  写盘丢弃、真实 home 前后哈希校验。
- **不可信内容**：任务文本/工具输出/日志摘录一律按数据注入；反思 prompt 禁止执行其中
  指令；输出严格 JSON + 后端校验；不执行候选内容；RIP md fence + 脱敏。
- **越权边界**：角色 token 不能写运行时/技能/MCP/feature flag（现有端点 human-only）；
  RIP 只能是文档建议；角色自有目标的提案直接拒绝并提示正确通道。
- **成本**：单 item ≤60k tokens、单 suite ≤1.5M、单角色 ≤1 次评估/周；反思
  输出 ≤30k、10 分钟超时；每角色每日反思 1 次/每周 3 次；预算耗尽跳过并记录。
- **数据保留**：策略快照最近 20 个 + 每次晋级/回滚；eval 单例结果 180 天、聚合永久；
  RIP 随记录保留；清理走 maintenance 域。

### 6.1 使用体验影响评估（UX budget）

**结论：默认零影响；试点开启后有明确预算；任务永远优先于 RSI。**

| 维度 | 目标 | 机制 |
|---|---|---|
| 任务完成延迟 | p95 增加 <50ms | observation 是单条 DB event，无 LLM；反思异步、try/except |
| 角色被 RSI 占用 | 任务唤醒可抢占；RSI 不阻塞派发 | 可抢占 + 静默窗口 + 无待办任务才跑 |
| 任务板噪声 | 0 个新任务 | RSI 是 no-task run；只在角色卡显示 `evolving` |
| 额外 token | 默认 0；试点每角色 ≤100k/天反思、评估 ≤1.5M/周 | flags off + 预算 + 周上限 |
| 人工审批负担 | 试点 ≤30 分钟/周/角色 | 只有总是注入的 Strategy 需批；知识卡自主；批量 Inbox |
| UI 复杂度 | 关闭时完全隐藏 | Evolution/RIP 页按 flag 显示；任务详情“角色复盘”折叠 |
| 失败影响 | 任务不受影响；RSI 可 kill | try/except、kill switch、rollback、SOAKING |
| 存储 | 只对试点角色；快照 ≤512KB/版本；保留 20 版 | 上限 + 清理 |
| 首次迁移 | 旧角色行为不变 | 无标记时整份 instruction 视为 Charter；RSI 只写经验卡 |

**最可能影响体验的 4 个点及处置**：
1. 每任务 LLM 反思 → **不做**；两阶段（observation 立即、反思批量）。
2. RSI 占用角色导致任务等 → **可抢占**，任务优先，RSI 下次静默窗口重跑。
3. Inbox 候选过载 → dedupe、批量、只审总是注入的变更、拒绝理由归档。
4. 评估 token 高 → 默认 off、每周/每角色上限、只对 Strategy 评估。

**体验验收（P5）**：
- 任务完成 p95 延迟增加 <50ms；
- 试点期间因 RSI 导致的角色任务等待 = 0（被抢占次数单独记录）；
- 每角色每周人工审批 ≤30 分钟；
- 关闭所有 RSI flag 时，功能/延迟/UI 与 v1.48.x 无差异；
- 试点用户主观评分（1–5）≥4；<4 则回退 shadow 模式。

### 9.1 风险处理机制（预防 → 检测 → 恢复）

所有风险按同一套机制处理，不靠“设计时承诺”：

| 层 | 手段 | 落点 |
|---|---|---|
| **预防** | 三档权限 + 字段 allowlist + 有界编辑 + 隐藏集隔离（可选加密）+ evaluator 外部性 + 默认关闭 | §1、§2.5、§3.3、§3.9 |
| **检测** | observation 覆盖率、SOAKING/EWMA/CUSUM、A/A canary、integrity hash、预算/配额、人工抽检 | §2.7、§3.7、§3.9 |
| **恢复** | 版本快照 + 一键回滚 + SOAKING 自动回滚 + kill switch + 负结果归档 | §1.3、§2.7、§5.4、§5.8 |

**默认安全姿态**（任何未决问题未定时都按此执行）：
- `role_rsi=off`、`role_rsi_evaluation=off`、`role_rsi_rubric_judge=off`；
- 永不自动晋级；`inconclusive` 不晋级；
- 任何策略写入先快照、可回滚；RIP 永不自动应用；
- `rsi.kill_switch=1` 立即停止新 cycle/eval，在途 run 允许完成但不晋级；
- 关闭所有开关时，Anvil 现有行为不变（P1 验收项）。

**阶段门（Go/No-Go）**：

| Gate | 时点 | 决策 |
|---|---|---|
| G0 设计评审 | P0 前 | 确认三档、评估证据、RIP 形态；未决问题按下表取默认；架构护栏登记例外 |
| G1 Shadow | P1 结束 | observation 覆盖率 100%（done 任务参与者）；无越权写；无任务延迟回归；否则不进入 P2 |
| G2 评估 | P2 结束 | 回放可重复、A/A 噪声可测、样本不足输出 inconclusive；否则只保留只读评估，不开启晋升 |
| G3 候选 | P3 结束 | 至少 1 次完整候选→评估→人工晋级→SOAKING→回滚（演练）；否则不进入 P5 |
| G4 试点 | P5 结束 | 见下方 pilot 判据；未达标则只发布 observation + RIP + 只读评估，`role_rsi` 保持 off |

**P5 试点判据**：
- 至少 1 个角色、4 周、≥20 个 done 任务；
- 至少 1 次真实晋级 + 1 次回滚（演练或真实）；
- held-out 有可复现提升（CI 下界 > noise floor），且无 safety/Charter 违规；
- 人工评审负担可接受（每角色每周 ≤30 分钟）；
- token 成本在 `rsi.daily_token_budget` 内；
- 若只达到“评估可读、提案有用”但无统计显著提升，**保留 shadow 模式**，不默认开启晋级。

**残余风险（明确接受并写入发布说明）**：
- 单机同 OS 用户下，隐藏集隔离/加密都不能硬防御拥有 shell 的恶意 agent；最终控制是
  人工复核 + evaluator hash + 不暴露路径。
- rubric judge 若开启，同模型家族偏好无法完全消除；κ 门槛 + 人工抽检 + L2 校验。
- 单用户样本少时，统计功效有限；系统输出 `inconclusive`，由人决定是否 override。
- 人工评审仍是瓶颈；通过批次 Inbox、diff/评估 UI、只审总是注入的变更来控制。

### 9.2 未决问题的默认决策与解决时点

每个未决问题都给一个**可实施的默认值**，不阻塞 P0；到对应 Gate 由 owner 确认或改默认：

| # | 未决问题 | 默认决策 | 决策时点/负责人 | 若默认不可行的回退 |
|---|---|---|---|---|
| 1 | `instruction.md` 是否立即引入 Charter/Strategy 标记 | **P0 引入标记 + UI“一键拆分”**；未拆分前整份视为 Charter，RSI 只改 PRINCIPLES/经验卡 | G0 / owner | 人工手工插入标记；RSI 仍可运行，只是不改 instruction |
| 2 | L2 回放用 shadow data dir + 临时 home，还是临时 shadow 角色行 | **shadow data dir + 临时 role home**（不产生角色行）；若 runtime 投影强制需要角色行，用 `kind='eval'` 隐藏角色，结束即清理 | G2 / 实现 owner | 用一次性 runtime 调用做非 agentic 回放；agentic 回放延后 |
| 3 | 隐藏集是否加密 | **默认不加密**：独立目录 0700 + ACL + 不暴露路径/ID + 审计为主防线；`rsi.eval.encrypt_hidden=1` 时启用 AES-GCM + `cryptography` + `ANVIL_EVAL_KEY` | G2 / owner | 机器共享/备份不可信时开启加密；不开启时明确标注 residual risk |
| 4 | RIP 导出到 `docs/runtime-proposals/` 是否默认 git 跟踪 | **导出但不自动 git add/commit**；由 human 决定是否入库 | G4 / owner | 只保留 `data/runtime-proposals/`，需要时手动复制 |
| 5 | 是否停用 agent 的 `anvil self edit-instruction` 直写 | **`role_rsi_lock_strategy` 开启时转审批候选**；全局默认 off，试点角色必须开启 | G1/G3 / owner | 保留直写但强制快照 + 审计；不推荐，会绕过三档 |

## 11. SDD / TDD 实施规范

### 11.1 交付顺序与 Gate

```
设计文档归档 → Spec 编写 → Spec 评审（S0 Gate）→ P0…P5 TDD → P6 试点 → 发布确认
```

- **S0 Gate**：spec 通过用户评审后，才允许写实现代码；
- 每个阶段结束跑该阶段验收 + 全量回归，未通过不进入下一阶段；
- 发布前必须再次与用户确认版本号（遵循“提交前确认版本号”规则）。

### 11.2 Spec 结构（`docs/superpowers/specs/2026-11-24-anvil-role-rsi-spec.md`）

1. 元信息：状态、日期、关联设计文档 `docs/v1.50-role-rsi.md`、范围；
2. Context / Goals / Non-goals；
3. 术语：Charter、Strategy、Experience、EvolutionVersion、ConfigRevision、Candidate、
   RIP、SOAKING；
4. **需求表**：每行 `ID | 标题 | 优先级 | 验收（Given/When/Then）`；
   建议 ID 段：
   - `RSI-VER-*` 版本/存档/切换/导出导入；
   - `RSI-OBS-*` 完成回执/触发/上下文隔离；
   - `RSI-EVAL-*` 回放/统计/诊断/漂移；
   - `RSI-CAND-*` 候选/算子/晋级/回滚；
   - `RSI-RIP-*` 运行时提案；
   - `RSI-SEC-*` 安全/完整性/HITL；
5. 数据模型与迁移（表/列/索引/回填）；
6. API / CLI / UI 契约（请求/响应/错误码/权限）；
7. 不变量与安全（单写者、Charter guard、隐藏集隔离、预算）；
8. **测试矩阵**：`需求 ID → 测试文件::用例 → 阶段`；
9. 阶段计划与退出标准；
10. 风险与未决（对应设计文档 §9）；
11. 参考。

**SDD 规则**：
- Spec 是唯一真相源；实现与 spec 冲突时先改 spec + 测试，再改代码；
- 每个任务/提交引用 spec ID；禁止“代码先行、事后补 spec”；
- 需求变更必须更新测试矩阵与变更日志。

### 11.3 TDD 循环（每个需求）

```
1. 写失败测试（红），测试名/注释引用 spec ID
2. 最小实现（绿）
3. 重构（保持绿）
4. 跑目标测试 + 全量 pytest
5. 更新测试矩阵状态
```

规则：
- 后端 pytest：使用 `dev/tests` 约定与 `conftest.py` 隔离数据目录；
- 迁移测试：临时 DB，断言幂等/回填/回滚；
- API 测试：httpx `AsyncClient` + ASGITransport；覆盖 agent 403、human 成功、错误码；
- CLI 测试：subprocess 契约，覆盖 help/参数/输出；
- Graph 测试：`_run_prompt_kind`/协议快照/投影，锁定 run 分类；
- 外部模型/运行时用 fake/stub；不 mock SQLite，用临时真实 DB；不联网；
- 统计测试固定 seed/fixture，断言 verdict 三态与 CI 方向；
- 前端：仓库无单测框架，**不强行引入**；以 `npm run build` + CDP 手测为主，
  纯过滤/徽标逻辑可选 Vitest（需 owner 同意）；不得以“手测通过”替代后端 TDD；
- 新增代码不降低现有覆盖率；每个 spec 验收至少 1 个自动化测试（前端可 CDP 脚本）。

**Definition of Done（每个任务）**：
- 先有失败测试记录；
- 目标测试 + 全量 `pytest` 通过；
- 无新增 skip；无网络/真实模型依赖；
- 审计/事件/权限已覆盖；
- spec 测试矩阵更新；
- 功能开关默认 off（除显式说明）。

## 12. v1.50 实现对齐补充（2026-11-25）

本节把设计阶段的概念与最终落地代码对齐，作为 P6 试点和后续维护的入口。若与前面章节
存在措辞差异，以本节和 Spec 的验收条款为准。

### 12.1 三套上下文与信息流

| 上下文 | 载体 | 输入 | 不可见 |
|---|---|---|---|
| 任务执行 | 角色常驻 daemon，按 task/slice 分槽 | 任务、active Strategy/Experience、任务知识 | 隐藏评测集、verifier、RSI transcript、evaluator 代码 |
| RSI 反思 | `origin=rsi_reflect` 一次性 run，`__rsi_reflect__` 槽 | 脱敏证据包、Strategy、聚合 diagnosis、算子统计、负结果 | held-in/held-out item 内容/ID、verifier、任务会话 transcript |
| L2 评估 | `ReplayRunner` + 临时 shadow home/workspace | 版本 manifest、item prompt、隐藏 verifier（仅 evaluator） | 真实角色 home、Anvil endpoint/token、隐藏集路径/ID |

信息流只允许：

```
任务证据 ──脱敏摘要──► RSI 反思 ──候选/知识/RIP──► 人工审阅
评估 ──聚合 diagnosis/Δ/CI──► RSI 反思
RSI ──候选 manifest──► 评估
```

### 12.2 反思闭环（observation → evidence → ingest）

- **observation 立即、确定性、幂等**：任务 done/驳回/步骤失败/返工同步写
  `events(source='rsi_observation')`；唯一键含 `role|task|completion_key`。
- **按角色试点门**：`rsi.role_enabled` = 全局 `role_rsi` 且
  `definition.rsi.enabled=true`；未启用的角色不写观测、不反思、不建 run。
- **批次反思**：scheduler `evolution.rsi_dispatch_reflections` 只在角色无活跃任务、
  全局活跃 run 未超限、触发策略满足时创建 run；任务唤醒可抢占。
- **证据包**（`rsi.build_evidence`）：
  - 最近 observation + retro 摘要（脱敏 token/密钥/绝对 home 路径）；
  - active version、工作集 hash/count；
  - 最近一次 `eval_runs.diagnosis`（只给聚合值，不含 item ID）；
  - 候选状态统计、负结果摘要、`rsi.focus.<role>`；
  - 不含 held-in/held-out 内容或 verifier。
- **反思输出入库**（`rsi.reap_reflections`）：
  - 解析 run log 最后一个 `[result]` 后的 JSON；
  - `knowledge_items`（scope=role）→ 角色经验卡（受自主档/质量/去重/禁词门）；
  - `edits` → 自主卡直接写；审批档 → `proposals(kind=strategy,status=draft)`；
  - `role_proposals` → 现有 portrait proposal allowlist；
  - `runtime_issues` → `runtime_proposals` draft/evidence；
  - 每 run 只入库一次，写 `rsi.reflection_ingested`；失败/解析失败也记审计。
- **tier 不可伪造**：`rsi_operators.validate_edits` 从固定算子目录派生 tier；
  反思输出声称 autonomous 不能把审批档降级。

### 12.3 L2 回放执行（`services/eval_runner.py`）

一次 `ReplayRunner(item, version)`：

1. 复制真实角色 home 到临时 shadow（排除 logs/scratch/.anvil/CLAUDE.md），
   真实 home 前后 `_tree_hash` 必须一致；变化则中止评估。
2. 按版本 manifest 把 Strategy/Experience 文件从 CAS 物化到 shadow；
   不写真实角色 home。
3. 创建临时 workspace；`git_snapshot` 支持从 `REPOS_DIR`/本地路径 clone +
   checkout commit；执行 item `setup`。
4. 用版本投影生成运行时的 instruction 文件（CLAUDE.md/GEMINI.md 由 runtime
   YAML 决定），注入 Strategy/PRINCIPLES/经验卡；使用回放协议。
5. 以角色 runtime 执行 item prompt；环境不含 `ANVIL_ENDPOINT`/`ANVIL_TOKEN`/
   `ANVIL_EVAL_KEY`，设置 `ANVIL_EVAL_MODE=1`；解析 token usage。
6. evaluator 自己执行隐藏 verifier checks；角色看不到 verifier 命令。
7. 计算 `score`（加权通过率）、`hard`（candidate hard check 失败）、
   `forbidden`（forbidden paths 被改动）、token cap/超时。
8. 返回给 `role_eval` 做配对统计；baseline hard failure 不否决 candidate，
   只有 candidate hard/forbidden 触发 reject。

**评估队列**：

- `role_eval.enqueue` 写 `eval_runs(status=queued, request_json=...)`；
- `EvalWorker` 单并发消费；`evaluation` 开启且应用启动时创建；
- 评估完成原地更新同一条 `eval_runs`，候选状态：
  `evaluating → pending`（promote/inconclusive）或 `rejected`（reject）；
- promote 仍必须人工批准；inconclusive 永不自动应用。

**默认关闭原因**：两臂回放成本高、需要人工策展 ≥8+8 真实任务和确定性 verifier；
数据不足只会 `inconclusive`；隔离/工作区副作用需要试点验证。当前真正控制
ReplayRunner 的是 `role_rsi_evaluation`；`role_rsi_replay_l2` 是预留开关，尚未单独生效。

### 12.4 版本、工作集与配置修订

- **演进版本 `kind=evolution`**：Strategy + Experience 文件 + 角色知识卡 +
  definition/charter_digest；由基线/候选/晋级/切换产生。
- **配置修订 `kind=config`**：人工 profile/tools/catalog/runtime/instruction 历史；
  默认隐藏；新修订保存 definition + instruction/PRINCIPLES manifest +
  `role_tools_json`；不保存 playbooks/经验卡。
- **工作集**：active manifest 之外的 RSI 角色卡；run 记录
  `runs.working_set_hash`；评估记录 baseline/candidate 双侧 hash；晋级时固化。
- **应用演进版本**：
  - 非 active 行“应用”，active 行“重新应用”；底层同一个 `switch`，只是目标版本不同；
  - 先调用只读 `preview_switch` 返回文件 added/modified/unchanged、知识卡
    恢复/归档/人工保留、Charter 差异、工作集；UI diff 后二次确认；
  - 确认后恢复 Strategy/Experience、归档不在快照内的 RSI 卡、保留 human 卡；
    Charter 默认不恢复；不重跑评估。
- **恢复配置修订**：恢复 definition + manifest 策略文件 + `role_tools_json`；
  不改变 active evolution；legacy 修订给 warning；写 `role.config_restored`。
- **配置修订去重**：`_snapshot_version` 使用 charter_digest（definition +
  role_tools + instruction Charter）做 no-op 去重；重复保存只累加 `coalesced_count`；
  演化页可“清理重复配置修订”（每组保留最新一条，soft delete）。
- **导出**：仅 evolution；zip 含 `export.json/manifest.json/manifest.sha256/
  charter.json/files/README.md`；不包含 logs/task/shared/eval/密钥。
  `charter.json` 的 tools 取导出时当前 `role_tools`，不是版本时快照（已知限制）。

### 12.5 调度、试点门与策略锁

- scheduler 第 11 域 `evolution`（`maintenance` 后）：
  - `rsi_dispatch_reflections`
  - `rsi_reap_runs`
  - `rsi_soak_check`
  - `runtime_proposal_detect`
- `rsi_dispatch_reflections` 检查：每角色单活跃反思、无活跃任务 run、
  全局活跃 run < `ROLE_RSI_MAX_GLOBAL_ACTIVE_RUNS`（默认 2）、冷却/日/周配额。
- `role_rsi_lock_strategy=1` 且角色已启用 RSI 时：
  - agent 直写 instruction 拒绝（Charter/Strategy 均不可绕过）；
  - agent `append principle` 转 pending 候选；
  - human 直写仍可用。
- `definition.rsi.enabled` 由 human 在演化页或 `PUT /roles/{slug}/rsi` 开启；
  推荐先只对 2–3 个试点角色开启。

### 12.6 运行时改进提案与自动检测

- **RIP 入口**：
  - 角色运行中 `anvil runtime propose` / 反思 `runtime_issues`；
  - human/agent 通过 API/UI 创建 draft/追加 evidence；
  - 确定性 detector。
- 组件类型：skill、mcp_server、runtime_yaml、feature_flag、tool_preset、model、
  environment、harness_part；禁止 eval/security/anvil-source/role-config。
- 生命周期：`draft→open→triaged→accepted→implemented→verified→closed`，
  另有 rejected/duplicate/wontfix/stale；agent 只能 draft/evidence，human 独占流转/导出。
- **自动检测当前实现**只覆盖：
  - `runtimes.status in (missing,unhealthy)` → environment draft；
  - `runs.failure_class in (platform_timeout,spawn_error,context_overflow)` → draft。
- 检测器按签名去重，但失败 run 目前用 `run:<run_id>` 作为 component_key，
  不同 run 不会合并成同一条；且 scheduler 每 tick 运行（默认 5s），不是严格每日。
  这两点是 P6 前可优化的噪声项。
- `runtime_proposals` 默认开启（只生成文档，不自动应用）；
  `runtime_proposal_detector` 默认关闭（避免自动工单噪声）。

### 12.9 已知边界与 P6 前待办

1. P6：2–3 个真实角色 4 周试点，验证任务 p95 增量、人工评审时间、token 预算、
   held-out 提升与 go/no-go。

   也纳入 evolution 版本并导出。

6. P6 若只达到“评估可读、提案有用”但无统计显著提升，保留 shadow 模式，不默认开启晋级。
